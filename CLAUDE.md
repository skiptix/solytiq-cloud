# CLAUDE.md — Solytiq Cloud


CRITICAL SYNCHRONIZATION RULE: Whenever you make changes, updates, or additions to this CLAUDE.md file, you MUST immediately apply the exact same modifications to the GEMINI.md and .antigravity.md file in the repository root. ---

Solytiq Cloud is a self-hosted, full-stack productivity suite: task lists, project timelines, file sharing, shared workspaces, a GPS/GPX route planner, and an AI assistant. The stack is React 19 + Vite (frontend), Express + TypeScript (backend), PostgreSQL 16, and Nginx — orchestrated with Docker Compose.

The current version is displayed at the bottom-left of the sidebar in `frontend/src/components/Sidebar.tsx`.

## Development Setup

### Prerequisites

- Docker + Docker Compose (recommended for full stack)
- Node.js 22+ (for local frontend/backend development)
- PostgreSQL 16 (if running backend without Docker)

### Running with Docker Compose (recommended)

```bash
cp .env.example .env          # fill in POSTGRES_PASSWORD, JWT_SECRET
docker compose up --build
```

Frontend is served at `http://localhost` (port 80 via Nginx).

**First run:** if no users exist yet, the backend logs a one-time **setup token** (see `setupToken.ts`). Use it on the `/setup` wizard to create the first (admin) account.

### Running locally without Docker

**Backend:**
```bash
cd backend
npm install
# Ensure PostgreSQL is running and PGHOST/PGUSER/PGPASSWORD/PGDATABASE env vars are set
npm run dev        # ts-node-dev with --respawn, port 3001
```

**Frontend:**
```bash
cd frontend
npm install
npm run dev        # Vite dev server, port 5173 with HMR
```

When running the frontend separately, point it at the backend with `VITE_API_URL` (the API client defaults to `/api`), or add a `/api` proxy to `vite.config.ts` (none is configured by default).

## Environment Variables

Copy `.env.example` to `.env` at the repository root. Docker Compose reads this file automatically.

| Variable | Required | Description |
|---|---|---|
| `POSTGRES_DB` | Yes | Database name (default: `solytiq`) |
| `POSTGRES_USER` | Yes | DB username (default: `solytiq`) |
| `POSTGRES_PASSWORD` | Yes | DB password — must be changed in production |
| `JWT_SECRET` | Yes | Long random string for signing JWTs — **fails startup if default** |
| `FRONTEND_URL` | Yes | Origin allowed by CORS (e.g. `http://localhost`). When unset, CORS allows `*` without credentials. Also used as the public origin for OAuth/MCP discovery when `PUBLIC_URL` is unset |
| `PUBLIC_URL` | No | Public origin (scheme + host) for OAuth issuer/endpoints and the MCP resource pointer. Falls back to `FRONTEND_URL`, then the request's forwarded host |
| `PORT` | No | Backend listen port (default: `3001`); also the host port for the frontend container |
| `OPENROUTER_API_KEY` | No | Enables the AI assistant via OpenRouter |
| `OPENROUTER_MODEL` | No | Model name (default: `openai/gpt-4o-mini`) |
| `NUKE_SKIP_RESTART` | No | Set to `true` to stop the admin Nuke action from calling `process.exit(0)` at the end — only needed when running the backend without a process supervisor (e.g. plain `node dist/index.js`, no Docker restart policy) that would otherwise bring it back up |
| `RESEND_ENCRYPTION_KEY` | No | Dedicated key for encrypting the Resend API key at rest in `app_settings` (see Email Notifications). Falls back to a key derived from `JWT_SECRET` when unset — the Resend key itself is configured from the admin UI, not an env var |

The backend refuses to start in `NODE_ENV=production` if `JWT_SECRET` is the default placeholder.

The GPS route planner calls public upstreams (Overpass for POIs, Valhalla for road snapping/routing). Outbound IPv4 is forced at startup (`dns.setDefaultResultOrder('ipv4first')`) because containers often advertise non-routable IPv6.

## Backend Conventions

### Database

- **No ORM.** All queries use raw SQL via the `pg` client (`pool.query` / `query` helper from `db.ts`).
- **Schema migrations** run automatically at startup inside `runMigrations()` in `index.ts`. New columns use `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` so they are additive and safe to re-run.
- **Never add a separate migration file** — append `pool.query(...)` calls to `runMigrations()` in `index.ts`. `runMigrations()` also performs idempotent data heals/seeds (e.g. auto-creating a "Personal" workspace per user, re-syncing list items to their list's workspace).
- Task IDs are `BIGINT` (numeric, generated client-side as `Date.now()`). Most other entity IDs are `VARCHAR(100)` strings (uuid package or timestamp-based). User and workspace-member IDs are `UUID` from `pgcrypto`'s `gen_random_uuid()`.

### Core Data Model

| Table | Purpose / key columns |
|---|---|
| `users` | `id UUID`, `username`, `email`, `password_hash`, `is_admin`, `token_version` (JWT invalidation), `profile_image`, `totp_secret`/`totp_enabled` (2FA), `last_online`, `email_notification_prefs JSONB` (sparse per-`NotificationType` email on/off overrides — see Email Notifications), `meeting_reminder_lead_minutes` (0 = off, default 30) |
| `lists` | List metadata + `is_public` (workspace visibility), `folder_id`, `workspace_id`, `parent_task_id`/`depth` (sublists), `view_mode` (`list｜kanban｜timeline` — the Board screen's layout, per list), `is_archived`/`archived_at` (hidden from the normal workspace view — see Automation Hub), `quick_add_enabled`/`quick_add_kb_entry_id`/`quick_add_memory_dirty` (see Board Screen: Quick Add), and share-link columns (`share_token`, `share_enabled`, `share_password_hash`, `share_expires_at`, `share_subpages`, `share_view_mode` — nullable override of which layout the public page renders) |
| `sections` | Ordered groups within a list (`list_id`, `label`, `emoji`, `position`) |
| `tasks` | `id BIGINT`, `source` `'dash'｜'list'`, `list_id`/`section_id`, `linked_list_id`/`linked_list_type` (`'sublist'｜'link'`), `workspace_id`; `updated_at` maintained by a trigger |
| `folders` | Groups lists/timelines; `is_public`, `collapsed`, `workspace_id` |
| `timelines` | Milestone-based views: `layout` (`vertical｜compact｜detailed`), `is_public`, `folder_id`, `workspace_id`, share-link columns (`share_token`, `share_enabled`, `share_password_hash`, `share_expires_at`) |
| `milestones` | `timeline_id`, `title`, `milestone_date`, `time_val`, `status` (`upcoming｜in-progress｜done`), `position` |
| `workspaces` | `visibility` (`private｜public`), `owner_id`; each user is auto-seeded a private "Personal" workspace; `agent_mode` (`off｜suggest｜assisted｜autonomous`) + `agent_policy JSONB` (see Agent Runtime) |
| `workspace_members` | `(workspace_id, user_id)` PK, `role` (`owner｜member`) |
| `shared_files` | File sharing: `share_token` (unique), `is_public`, `password_hash`, `expires_at`, `title`, `note` |
| `task_attachments` | Files attached to tasks: `attachment_type` (`upload｜linked`), optional `shared_file_id` |
| `milestone_attachments` | Files attached to milestones — same shape as `task_attachments` (`milestone_id` FK, `upload｜linked`) |
| `gps_files` | `file_type` (`gpx｜fit`), `file_path`, `metadata JSONB`, `smoothed`, `route_state JSONB` (Route Planner State v1) |
| `meetings` | Standalone calendar events (no list/timeline/workspace), owned by `user_id`: `title`, `meeting_date`, `start_time`/`end_time`, `all_day`, `location`, `color`, `caldav_uid` (CalDAV resource mapping), `recurrence_id` (shared by every occurrence of a repeating series) |
| `meeting_attendees` | `(meeting_id, user_id)` PK — instance users invited onto a meeting by its organizer; the meeting appears on their calendar too, read-only |
| `caldav_credentials` | Per-user CalDAV app password: `user_id` PK, `password_hash` (bcrypt), `last_used_at` |
| `mobile_connections` | One row per signed-in mobile device (Solytiq Cloud iOS app): `user_id`, `device_name`/`device_model`/`os_version`/`app_version`, `created_at`, `last_seen_at`. The row id is embedded in the device's JWT (`connectionId`) so it can be listed and revoked |
| `homescreen_connections` | One row per iOS "Add to Home Screen" install: `user_id`, `install_id` (client-generated, localStorage-persisted, unique per user), `device_name`/`os_version` (parsed client-side from the UA), `created_at`, `last_seen_at`. Upserted by `POST /api/auth/homescreen-connections/ping` on every standalone launch — unlike `mobile_connections`, there's no separate JWT/session to bind, since it's the same web login running in standalone display mode |
| `user_invitations` | Admin-by-email account invitations (see User Invitations): `email`, `token_hash` (SHA-256 of the one-time link token — the raw value is never stored), `is_admin` (role the accepted account gets), `invited_by`/`accepted_by` (nullable `users` FKs), `accepted_at`/`revoked_at` (both NULL = still pending), `expires_at` (7-day TTL) |
| `trash`, `trash_lists`, `trash_folders`, `trash_timelines` | Soft-delete payloads as JSONB with a 30-day `expires_at` |
| `templates` | User-owned, workspace-agnostic snapshot of a list's or timeline's full structure: `type` (`list｜timeline`), `is_shared` (visible read-only to every other instance user), `structure JSONB` (versioned tree built/consumed by `templateUtil.ts`) |
| `automations` | Per-workspace flow-chart automation: `workspace_id`, `user_id` (creator = sole editor), `enabled`, `graph JSONB` (nodes/edges, validated by `automationGraph.ts`), `trigger_type`/`trigger_scope JSONB` (denormalized from `graph` for an indexed lookup), `next_fire_at` (schedule triggers), `version` (optimistic concurrency) |
| `automation_runs` | Execution log for one automation firing: `trigger_type`, `trigger_context JSONB`, `status` (`running｜success｜failed`), `steps JSONB` (per-action result), `error`, `is_test` (real-run started from the editor's per-node Test button rather than a live trigger) |
| `installed_apps` | Admin-installable App Directory catalog state (Settings → System → Discover Apps): `app_id` on/off per instance. Catalog itself is code (`appsRegistry.ts`) — `gps`, `files`, `mcp`, `automations` |
| `app_settings` | Key/value config (storage quota, `ai_assistant_enabled`, `ai_model`, `two_fa_feature_enabled`, `mcp_enabled`, `mobile_app_enabled`) |
| `notifications` | Per-recipient notification feed (User Notification System): `user_id` (recipient), `type` (`workspace_added｜item_invite｜meeting_invite｜item_tagged｜mention｜automation_run｜deadline_overdue`), `actor_id` (nullable — null = system), `title`/`body`, `entity_type`/`entity_id`/`workspace_id` (deep-link target), `data JSONB`, `dedupe_key` (partial-unique per recipient — overdue sweep alerts once), `read_at`. Written only via `notifications.ts`; an AFTER-INSERT sync_log trigger pushes a `notification` signal to the recipient |
| `task_tags` | Users tagged onto an item (task): `(task_id, user_id)` PK, `tagged_by`. Only the EXTRA tagged users — the item creator is the implicit owner, shown in the dialog's Tag row but never stored here. A new tag notifies the tagged user |
| `item_shares` | Per-item invitations ("Shared with members"): polymorphic `(item_type, item_id, user_id)` PK (`item_type` `list｜timeline｜markdownList｜folder`), `invited_by`. Grants one user **full-collaborator** access (view + edit content) to a single board/timeline/markdown page/**folder** independent of workspace membership. A grant is stored on the ONE row a human invited on, but RESOLVED over the containment tree (folder → its items, page → its Todo mirror, board → its sublists) — see "Per-item invitations" below. `include_all` (folder invites only, default true) is the invite dialog's scope choice: hand over the folder's contents too, or the folder alone. No FK on `item_id` (polymorphic) — the item's delete path clears its rows via `deleteItemShares()` (folders via `softDeleteFolderExec`). Written via `itemShares.ts` / `routes/itemShares.ts`; a new invite notifies the invited user |
| `ai_chat_sessions`, `ai_chats`, `ai_chat_files`, `ai_usage` | AI conversations, messages, uploaded files (30-day TTL), and per-call token usage |
| `section_placement_events` | Quick Add **history** — append-only: `list_id`, `task_id`, `title`/`title_key`, `from_section_id`/`from_section_label`, `to_section_id`/`to_section_label`, `event_type` (`created｜moved｜staged｜deleted`), actor, `occurred_at`. Section ids carry NO foreign key, alongside a label snapshot, so history stays readable after a section is renamed or deleted. **Never read by the predictor** — see "Board Screen: Quick Add" |
| `section_memory` | Quick Add **projection** — `PRIMARY KEY (list_id, title_key)`, `title`, `last_section_id` (FK, `ON DELETE CASCADE`), `occurrences`, `last_seen_at`, and (only when pgvector is present) `embedding vector(1536)` with an HNSW index. Exactly one row per (board, item title), holding that item's LAST section. The PK is what makes "only the last placement may drive a suggestion" a schema invariant rather than a filter a query could omit |

### Authentication

- JWT tokens are generated in `auth.ts` (`generateToken`) and verified via the `verifyToken` middleware in `middleware.ts`, which sets `req.userId`. Sessions last **30 days** (`SESSION_TTL` in `auth.ts`) so the frontend's account switcher can keep a second account usable that long — length is not the security boundary, `token_version` below is.
- Tokens embed a `token_version`; bumping `users.token_version` invalidates all of a user's existing tokens (used on password change / forced logout).
- **TOTP 2FA** (`otplib` + `qrcode`): when enabled, login returns a pending token and the client must call `/api/auth/2fa/verify`. Gated by the `two_fa_feature_enabled` app setting.
- Passwords are hashed with `bcryptjs`. Never store or log plaintext passwords.
- All routes except `/api/auth/login`, `/api/auth/register`, `/api/auth/request-setup-token`, `/api/auth/invitations/*` (see User Invitations below), the public `/api/share/*` endpoints, and `/health` require auth. The SSE endpoint `/api/events` authenticates via `?token=` query param or `Authorization` header.
- **Mobile app connections** — the iOS client sends `client: 'mobile'` + a `device` descriptor on `/api/auth/login` (and `/2fa/verify`); the server records a `mobile_connections` row and embeds its id in the JWT as `connectionId`. `middleware.ts` validates that connection on every request, so a user revoking a device (`DELETE /api/auth/mobile-connections/:id`, surfaced in Account Settings → Mobile) or an admin disabling the `mobile_app_enabled` setting (Settings → Mobile) signs the device out on its next call. `GET /api/auth/feature-flags` exposes `mobileEnabled`.
- **iOS Home Screen app tracking** — the frontend detects standalone display mode (`window.matchMedia('(display-mode: standalone)')` / `navigator.standalone`, `utils/homescreen.ts`) and pings `POST /api/auth/homescreen-connections/ping` with a locally-persisted `installId`, upserting a `homescreen_connections` row. This rides the same web JWT as any browser tab — no separate `connectionId` — so `DELETE /api/auth/homescreen-connections/:id` (surfaced in Account Settings → Mobile, alongside the native app's device list) only forgets the tracked row; it can't sign the device out, and the row reappears on next launch.

### User Invitations

Admin-initiated account creation by email (Settings → Users → **Invite User**), the second way (besides the owner-only first-run Setup Wizard and admin-set-password **Add User**) a new account ever comes to exist on an instance — there is no public self-registration anywhere in the app.

- **`user_invitations`** (see Core Data Model) holds one row per invite. Only a SHA-256 hash of the raw one-time link token is ever stored (`backend/src/userInvitations.ts`, same convention as `api_tokens`/`admin_api_keys`) — the raw token is returned to the inviting admin exactly once, in the `POST /api/admin/invitations` response, and is never retrievable again. A row is **pending** (still redeemable) exactly when `accepted_at` AND `revoked_at` are both NULL and `expires_at` is in the future (7-day TTL, `INVITATION_TTL_MS`); re-inviting the same email first revokes any still-pending invite for it, so at most one link is ever valid per address.
- **SECURITY — uniform 404, always.** `GET /api/auth/invitations/:token` (prefill check) and `POST /api/auth/invitations/:token/accept` (complete registration) are unauthenticated by necessity and return a **plain 404** for every invalid case — token never existed, already accepted, revoked, or expired — with zero distinguishing detail. `findPendingInvitation()` is the one function both routes go through, collapsing all of those into a single `null`. The frontend mirrors this exactly: `AcceptInviteScreen.tsx` renders the same `NotFoundScreen` for a 404 as it would for a URL that was never real — there is no "this invite was already used" message anywhere, by design (see `userInvitations.ts`'s header comment).
- **Accepting is transactional** (`routes/auth.ts`): the invitation row is locked with `SELECT ... FOR UPDATE` inside the same transaction as the `INSERT INTO users` and the `accepted_at` write, closing the double-accept race where two concurrent requests for the same link both see it as pending. `ensurePersonalWorkspace()` runs in the same transaction, exactly like `/register`. Deliberately does **NOT** auto-login (unlike `/register`) — a public, emailed link is not the place to silently establish a session — the new user is sent to `/login` instead.
- **Admin endpoints** (`routes/admin.ts`, `requireAdmin`): `POST /invitations` (body `{email, isAdmin?}` — rejects an email already in use with 409) creates the invite and attempts to email it via the shared Resend pipeline (`buildNotificationEmail`/`sendEmail`, see Email Notifications), but **never blocks on send failure** — the response always includes `inviteUrl` (built from `PUBLIC_URL`/`FRONTEND_URL`, null if neither is configured) and an `emailSent` flag, so an admin can copy-paste the link manually when Resend isn't configured. `GET /invitations` lists every invite (any status) for the Users tab's **Pending Invitations** section, which filters to still-pending rows client-side rather than trusting a stored status column. `DELETE /invitations/:id` revokes a pending invite (a no-op, not an error, on an already-settled row).
- **Rate limiting**: both public invitation endpoints sit behind `setupLimiter` (5/hour/IP) — the same tier as `/register`, since accepting an invite genuinely is a second registration entry point.
- **The 404 page is real, not a redirect** (`frontend/src/screens/NotFoundScreen.tsx`): a `standalone` prop toggles between a full-page card (public routes, e.g. a dead invite link) and just the content block sized to fill whatever chrome it's embedded in (used as `AppLayout`'s own catch-all route inside the authenticated app, replacing what used to be a silent `Navigate to="/dashboard"` — an unmatched in-app path now genuinely says so instead of pretending it was a redirect).

### Account Switching (multiple signed-in accounts)

The **ProfileCard** (Sidebar, bottom-left) can hold several signed-in accounts and switch between them without re-entering credentials for 30 days — "Switch account" expands to the list of other accounts plus **Add account** (`modals/AddAccountModal.tsx`).

- **`useAccountsStore.ts`** is the persisted session vault (`solytiq_accounts`): one `StoredAccount` per signed-in account (`userId`/`username`/`fullName`/`email`/`profileImage`/`isAdmin`/`token`/`addedAt`). Its pure helpers (`isSessionFresh`/`pruneAccounts`/`upsertAccount`/`removeAccount`) are unit-tested directly; `SESSION_MAX_AGE_MS` mirrors the backend's `SESSION_TTL` so an entry past its window is pruned locally instead of being offered as a switch target that is guaranteed to 401.
- **There is NO server endpoint that mints a token for another user.** Adding an account is an ordinary `/api/auth/login` (password, plus the TOTP step when that account has 2FA on) — being signed in as someone else grants no shortcut whatsoever. Switching only re-activates a token the server already issued to that account; it never creates authority. This is the architectural reason an unregistered / never-logged-in user can't be switched to: no code path can produce a token for them.
- **The server is the identity authority on every switch.** `switchToAccount()` (`useAuthStore.ts`) calls `apiVerifySessionToken()` (`GET /auth/me` with the stored token) FIRST and applies the identity from **that response**, never the locally cached label — so editing `solytiq_accounts` in localStorage cannot impersonate or self-promote (a relabelled entry resolves to whoever the token really belongs to; a fabricated one is rejected and dropped). Revocation still flows through `users.token_version`, re-checked on every request.
- **A failed switch never strands the user.** A rejected token forgets just that entry, leaves the current session active, and re-prompts login for it. Likewise a wrong password while adding an account must not sign the active account out — `apiLoginAdditional`/`api2FAVerifyAdditional`/`apiVerifySessionToken` pass `silent401` so they bypass the global 401 → `signOut()` path, and `authToken` so they don't send the ambient credential. They also bypass `apiFetch`'s GET coalescing, which is keyed on path alone and would otherwise hand an explicit-token `/auth/me` probe another user's cached response.
- **Switching hard-reloads the page** (`window.location.assign('/dashboard')`) after clearing the persisted per-user stores (`resetPerUserState()`). Clearing the persisted ones is mandatory — `solytiq_app`/`solytiq_workspace` survive a load, so the next user would otherwise rehydrate the previous one's tasks. The reload then covers every *in-memory* store too (members, templates, automations, graph, agent, AI, GPS…) rather than depending on each present and future store being remembered here, and re-runs `App.tsx`'s mount loader, which keys on `currentWorkspaceId` and so wouldn't refire on its own.
- Signing out drops only the active account from the vault (this is also what the global 401 handler does, where the token is already dead); other stored accounts are left alone.

### Rate Limiting

Seven tiers defined in `index.ts`:
- `apiLimiter` — 600 req / user / min for authenticated `/api/*` traffic, keyed on the verified `userId` (decoded from the JWT for the key only — pre-auth requests fall back to IP). One busy tab can only exhaust its own budget, not the whole instance. `/api/events` (the SSE stream) and `/api/sync/*` (the delta-sync polls it drives) are exempt — they must never count like mutations.
- `authLimiter` — 10 req / 15 min (login, `/api/auth/2fa/verify`), keyed on IP
- `setupLimiter` — 5 req / 1 hour (register, `request-setup-token`, admin nuke), keyed on IP
- `linksLimiter` — 120 req / user / min for `/api/links/*` (Graph Layer), on top of (not instead of) `apiLimiter` — visibility-scoped edge queries are pricier than typical CRUD
- `graphLimiter` — 120 req / user / min for `/api/graph/*` (traversal/metrics — recursive CTEs, batch metrics), on top of `apiLimiter` and NOT exempted like `/api/sync/*`. `/api/canvases/*` sits behind `apiLimiter` only (plain CRUD, no extra tier)
- `knowledgeLimiter` — 60 req / user / min for `/api/knowledge/*`, on top of `apiLimiter` — search can trigger a live query-embedding call to an external provider, pricier than a plain trigram lookup
- `agentLimiter` — 20 req / user / min for `/api/agent/*`, on top of `apiLimiter` — starting a run kicks off a multi-turn LLM tool-calling loop, far pricier than any other endpoint in the app

### User Notification System

A per-user notification feed surfaced by a **bell in the `TopBar`** (left of the profile avatar; unread badge; opens a right slide-in panel covering ~1/3 of the screen, full width on mobile) and by the **Dashboard's Notifications block** (`RightColumn` in `DashboardScreen.tsx`, replacing the former WiP placeholder). Both read the same **`useNotificationsStore`** (`items`, `unreadCount`, mark-read/dismiss/clear, cursor pagination).

- **One general-purpose table (`notifications`)**, written ONLY through **`backend/src/notifications.ts`** (`createNotification`/`createNotifications`): recipient is never notified of their own action (recipient === actor is a silent no-op), and an optional `dedupeKey` makes a notification idempotent per recipient. Read/managed via **`routes/notifications.ts`** (`GET /api/notifications` (paginated + `unreadCount`), `GET /unread-count`, `POST /:id/read`, `POST /read-all`, `DELETE /:id`, `DELETE /` clear-all) — every row hard-scoped to the verified `req.userId`.
- **What generates a notification** (each best-effort, never breaks the mutation that triggered it): another user **adds you to a workspace** (`routes/workspaces.ts`), **invites you to a list/timeline/markdown page** (`routes/itemShares.ts`, see Per-item invitations), **invites you to a meeting** (`routes/meetings.ts`, newly-added attendees only), **tags you on an item** (`routes/taskTags.ts`), **@mentions you** in a note or markdown block (`mentions.ts`, see below), an **automation you own runs** (`automationEngine.ts`, live runs only — a Test run self-suppresses), or a **task deadline goes overdue** (`sweepOverdueDeadlines()` in `notifications.ts`, an hourly cron registered in `index.ts`'s `start()`; notifies the task's creator + everyone tagged on it, exactly once per (task, deadline) via `dedupeKey`).
- **Realtime**: the `notifications` table has an AFTER-INSERT `sync_log` trigger that emits a `notification` signal scoped to the recipient (`workspace_id` NULL, `owner_id` = recipient), so it rides the existing delta-sync pipeline. `notification` is a SIGNAL sync entity (in `SIGNAL_ENTITIES`); `App.tsx` bumps `entityRevisions.notification` and calls `useNotificationsStore.syncRefresh()` (refreshes the badge always; the loaded feed too once any surface has shown it). The bell/feed navigate to the notification's target via `notificationTarget()` (`utils/notifications.ts`), switching workspace first when needed.

### Email Notifications (Resend)

An additive channel on top of the in-app feed above, not a replacement — every notification still writes its `notifications` row exactly as before; a subset of types ALSO emails the recipient via [Resend](https://resend.com).

- **Admin-configured from the UI, not an env var** (Settings → Email, `SettingsScreen.tsx`'s `email` tab): enabled toggle, API key, from-email, from-name — all stored in `app_settings` (`resend_enabled`, `resend_api_key`, `resend_from_email`, `resend_from_name`) so they can change without a redeploy. The API key is **encrypted at rest** (`backend/src/resendCrypto.ts`, AES-256-GCM, key derived via HKDF from `JWT_SECRET` unless a dedicated `RESEND_ENCRYPTION_KEY` is set — the same pattern `totpCrypto.ts` already established for `users.totp_secret`) and **never round-trips to the client**: `GET`/`PUT /api/admin/settings` strip `resend_api_key` from the response and substitute `resend_api_key_configured` (bool) + `resend_api_key_hint` (last 4 chars) so the admin UI can show "configured, ends in ••••ab12" without ever seeing the real key. `PUT` treats an omitted `resendApiKey` as "leave unchanged" and an explicit empty string as "clear it" (`setResendApiKey()` in `email/resendClient.ts`). `POST /api/admin/settings/resend/test` sends a test email to the calling admin's own address so the whole pipeline (key, sender domain verification) can be checked without leaving Settings.
- **`backend/src/email/resendClient.ts`** reads the current settings fresh on every send (`getResendSettings()`) and degrades gracefully — same "check reality, no feature flag to keep in sync" contract as the Knowledge Layer's embedding provider: no key, disabled, or no from-address configured all just make `sendEmail()` return `{ok: false}` rather than throwing. The `resend` SDK client itself is cached per API key (not reconstructed per send) but the settings row is always re-read, so a rotated key takes effect on the very next send. **`backend/src/email/templates.ts`**'s `buildNotificationEmail()` renders the one shared branded HTML wrapper (inline styles only — email clients strip `<style>` blocks and CSS variables; deliberately outside the Animate-UI layer's "no raw CSS outside components" rule, which governs the app's own React tree, not server-rendered mail markup) around a heading/body/CTA; `getAppBaseUrlForEmail()` builds the absolute CTA link from `PUBLIC_URL`/`FRONTEND_URL` (no `Request` to fall back on here, unlike `publicUrl.ts`'s `getPublicBaseUrl()` — sweeps and notification writers run outside any HTTP request) and the CTA is simply omitted when neither is configured.
- **The hook lives in ONE place**: `notifications.ts`'s `createNotification()` — after a genuinely NEW row is inserted (never on an `ON CONFLICT DO NOTHING` dedupe no-op, or a repeat overdue-deadline sweep would re-email hourly) — calls `maybeSendEmail()`, which checks the recipient's `users.email_notification_prefs` (sparse per-type override JSONB, same "only overrides stored" convention as `keyboard_shortcuts`; an absent key falls back to `DEFAULT_EMAIL_PREFS`) and a per-type `shouldEmailNotification()` filter for cases where "every notification of this type" would be noise (an `automation_run` only emails when `data.status === 'failed'` — a successful run stays in-app only). Every one of the 11 `NotificationType`s is wired through this same hook by construction; only `workspace_added` defaults ON — every other type (including `mention`/`automation_run`/`meeting_reminder`, despite being user-configurable in the Notifications section) defaults OFF, so a fresh account's inbox stays quiet until the user opts more in, reachable by widening `DEFAULT_EMAIL_PREFS` later with no new plumbing.
- **Meeting reminders are new** (`meeting_reminder`, not previously a `NotificationType`): `backend/src/meetingReminders.ts`'s `sweepMeetingReminders()` (5-minute interval, registered in `index.ts`'s `start()`, same shape as `sweepOverdueDeadlines()`) finds today's timed (non-all-day) meetings and notifies the organizer + every attendee **on their own configured lead time** (`users.meeting_reminder_lead_minutes`, 0 = off, default 30) once the meeting is within that window — a per-`(meeting, recipient)` `dedupeKey` means it's harmless that a meeting sits inside the window across several consecutive sweeps. V1 scope, deliberate: only looks at `meeting_date = CURRENT_DATE`, so a reminder window spanning midnight isn't caught.
- **User preferences** (Account Settings → Notifications, `UserSettingsModal.tsx`'s `EmailNotificationsSection`): per-type toggles for the 4 default-on types plus a lead-time picker (Off/15/30/60/120 min) for meeting reminders, saved via `PUT /api/auth/email-notifications` (validates against an allow-list of known `NotificationType`s, same shape as `PUT /shortcuts`). `sanitizeUser()` (`routes/auth.ts`) exposes `emailNotificationPrefs`/`meetingReminderLeadMinutes` alongside `keyboardShortcuts`.
- **Known V1 gaps:** no digest/batching (each qualifying notification sends its own email immediately); no bounce/complaint webhook handling yet, so a permanently-dead recipient address is not auto-disabled; the CTA link always points at a generic in-app route resolved from `entityType` (`ctaForNotification()` in `notifications.ts`), not the frontend's richer `notificationTarget()` logic, to avoid duplicating route-building knowledge server-side.

### Item tagging + @-mentions (members-only, notify-only)

- **Item dialog "Tag" row** (`TaggedUsersRow.tsx`, in `TaskDialog.tsx`) — **replaces the old badge chips AND the Owner row**. It always shows the item **creator** as a non-removable "Owner" chip, plus any tagged users; the item's owner (or an admin) can tag/untag other **workspace members** (`POST`/`DELETE /api/tasks/:taskId/tags`). Tagging is **notify-only**: it never changes who can see the item — you can only tag someone already in the item's workspace, so a deep-link always resolves. (The `badge` column still exists and renders on cards; it's just no longer editable from the dialog.)
- **@-mentions in notes & markdown** — typing `@` in a `NotesEditor` (task notes + milestone notes) or a Markdown Page block opens a **`MentionPopover`** of workspace members (arrow/enter/tab to pick; `utils/mention.ts` does the pure caret/token math). Mentions are stored as plain `@username` text (no UUIDs in user-visible content). On save the backend (`mentions.ts` `notifyNewMentions`) extracts `@username` tokens, resolves them ONLY against the item's workspace members, **diffs against the prior text**, and notifies the newly-added ones — so a re-save never re-notifies. The resolver is a pure, bounded, case-insensitive lookup (no injection path).

### Per-item invitations ("Shared with members")

Beyond workspace membership, a user can be invited to a **single folder, board, timeline, or markdown page** — the "Invite people" control (People tab in `ItemSettingsModal`, via `ItemMembersSection.tsx`) and the "share just this item" branch of the tag/mention prompt. This is the collaboration primitive behind private-item sharing, and the **folder** case is how a whole working set gets handed over at once.

- **One polymorphic `item_shares` table** (`item_type` + `item_id` + `user_id`), managed only through **`backend/src/itemShares.ts`** (`addItemShare`/`removeItemShare`/`listItemShares`/`deleteItemShares`/`getSharedItemIdsForUser` + the `itemShareExists(alias, type)` SQL fragment and its runtime twin `isItemSharedWith`). Endpoints: **`routes/itemShares.ts`** (`/api/item-shares/:itemType/:itemId/members` GET/POST/DELETE — owner/admin invites, any viewer reads; a new invite notifies with `type: 'item_invite'`) and **`GET /api/shared-with-me`** (every item invited to the caller, fully hydrated).
- **A grant is stored where it was made, and RESOLVED over the containment tree.** Inviting someone to a folder does NOT fan out per-item rows; the access check walks the containment relationships instead: **folder** → every board/timeline/markdown page whose `folder_id` points at it, **markdown page** → its auto-managed Todo mirror (`todo_list_id`), **board** → its sublists, recursively (`lists.parent_task_id` → the owning task → that task's list). This is what makes "all its content automatically" literal rather than a sync job: an item added to a shared folder *after* the invite is already shared, and one moved out is already revoked, with no cleanup pass to forget to run. A folder invite carries a **scope** (`item_shares.include_all`, chosen in the People tab's "What they get" toggle and mirroring the public link's own `folders.share_include_all`): with it off the folder is shared ALONE, so every cascade branch — and only the cascade branches, never a direct grant — is gated on it. Re-inviting an existing member changes their scope instead of erroring, so the choice is never a one-way door, and a scope change deliberately does not re-notify. It also means revocation only exists where the grant does — `listItemShares` reports an inherited member as `via: 'folder'` with the folder's name, and the UI renders that row without a Remove button rather than offering one that would silently do nothing.
- **Lists are the one type whose walk lives in the database** (`item_share_grants_list(p_user, p_list_id)`, created in `runMigrations()`): sublists nest arbitrarily deep, PostgreSQL forbids a correlated `WITH RECURSIVE` inside a subquery, and one definition beats re-deriving the recursion at 20+ access-condition call sites. **Two gates keep it off the hot path.** Every generated fragment is prefixed with a **non-correlated** `EXISTS (… item_shares s0 WHERE s0.user_id = …)` guard, which the planner hoists into a once-per-statement InitPlan — a user with no invitations pays a single index probe for a whole scan. Past that guard, the list fragment tries the two cheap non-recursive branches first (direct-or-folder, and the Todo-mirror bridge) and only reaches the function when `parent_task_id IS NOT NULL`, i.e. for rows that are genuinely sublists — otherwise every collaborator would pay a recursive walk per row on every list query in the app.
- **Every resolver goes through `itemShares.ts` — never a hand-rolled `item_shares` lookup.** Besides the read fragment and the runtime check, the cascade also has to reach `graph/visibility.ts` (both `visibleCondition` and `canWriteEntity`, or a sublist of a folder-shared board would be writable yet 404 from `/api/graph`, `/api/links`, entity search and knowledge search) and `mentions.ts`'s `resolveMentionUserIds` (or `@`-mentioning a folder-invited collaborator would resolve to nobody and notify no one, with no error to notice). Both are covered by `itemShares.integration.test.ts`.
- **Access is honored on BOTH reads and writes.** Every folder/list/timeline/markdown **read** access-condition gets `OR itemShareExists(...)` (`objectPolicy.ts`'s `objectAccessCondition` for lists/timelines, `FOLDER_ACCESS` in `routes/folders.ts`, `routes/markdownLists.ts`'s own condition), so invited items appear via `getListForUser`/`buildListsForUser`/`getFolderForUser`, etc. **Full-collaborator** means the invited user may edit CONTENT: the content-write endpoints (task create/update/delete/reorder, section CRUD, milestone CRUD, markdown block content + image upload) allow `owner || admin || isItemSharedWith(...)`; only the owner/admin manages the item itself (rename/visibility/sharing/delete/invites — e.g. the markdown PUT applies metadata fields only for `canManage`). `itemShareExists` (SQL, reads) and `isItemSharedWith` (runtime, writes) resolve the SAME tree by construction — the list case calls the same DB function — because a user who can open a board but not edit it is the exact bug that split would cause.
- **A folder decides its new contents' workspace AND visibility** (`resolveFolderPlacement`, `routes/folders.ts`, used by the `lists`/`timelines`/`markdownLists` POST paths). A folder and its contents must share one workspace, so once a folder can be shared with a non-member, resolving a new item's workspace from the CLIENT's active workspace would drop it into a different workspace than the folder it claims to be in — a combination `runMigrations()` heals by nulling `folder_id`, i.e. the item silently jumps out of the folder the user just put it in. It also returns `inheritIsPublic`, set only when the folder belongs to SOMEONE ELSE: a collaborator adding a board to a folder shared with them would otherwise create it `is_public = false` under their own ownership — invisible to the folder's owner and every workspace member, an item that vanishes from the folder it was just added to for everyone but its author. (Other folder invitees see it either way; the cascade matches on `folder_id`, not on visibility.) A folder the caller can't see is dropped rather than rejected, matching `resolveWorkspaceForUser`'s fall-back-don't-fail posture.
- **Surfacing:** a **"Shared with me"** Sidebar section (`useSharedItemsStore` ← `/api/shared-with-me`) lists invited items from any workspace, de-duped against the active workspace's own items. A shared **folder** renders as a group with its own boards/timelines/pages nested under it, and only genuinely loose items stay at the top level — except on the collapsed rail, which has room for neither a heading nor indentation and so falls back to the flat icon-row list (grouping there would hide a folder's contents behind a folder icon). The endpoint hydrates through the BATCH builders (`getFoldersForUserBatch`/`getListsForUserBatch`/`getTimelinesForUserBatch`), since one folder invite expands to every board in it and this endpoint re-fires on focus, on an invite notification, and ~300ms after any mutation. `/api/shared-with-me` returns the folder plus its current contents, but deliberately NOT the deeper containment (sublists, a page's Todo mirror) — those are reachable, but they render under something already in the payload and would be bogus top-level rows. `ListScreen`/`TimelineScreen`/`FolderDashboardScreen` fall back to `useSharedItemsStore` when an item isn't in the workspace-scoped app store; `MarkdownListScreen` already loads by id (its GET honors invites). Because the delta-sync engine is workspace-scoped, edits to a cross-workspace shared item are **eventually-consistent** — the shared store refetches ~300ms after a write (guarded to users who actually have shares) and on invite notifications / focus, rather than instant SSE.
- **Every user-picker dropdown in a modal is portaled** (`components/AnchoredDropdown.tsx`, used by `ItemMembersSection` and `TaggedUsersRow`). Two independent things hide an in-place dropdown here, and fixing only one leaves it invisible: the modal card sets `overflow: hidden` with a scrolling body, which CLIPS an `absolute` panel regardless of z-index; and that same card is a `motion.div` with a transform, which per the CSS spec becomes the containing block for `position: fixed` descendants, so a fixed panel is still trapped inside the modal's bounds. Only a portal to `document.body` escapes both. The panel positions itself from the anchor's live `getBoundingClientRect()`, re-measuring on capture-phase scroll (the modal body's own scrolling does not bubble to window) — written straight to the node rather than through state, since a re-render per scroll event would also mean a `setState` in an effect body, which this codebase keeps at `error`.
- **Tag/mention share prompt:** `TaggedUsersRow` lets the owner tag any instance user; if the target can't yet see the item, a prompt offers **Share just this item** (`item_shares` invite to the task's list) or **Add to the whole workspace** (workspace member + item invite, so a private item stays visible). `@`-mentions resolve against workspace members **∪** item invitees (`resolveMentionUserIds`'s `shareItem` scope), so `@` works even in a solo-workspace page you've shared with someone.
- **Tests:** `itemShares.test.ts` (mock `QueryExec`) pins which SQL is ISSUED and that reads/writes resolve the same tree; **`itemShares.integration.test.ts` covers what a mock structurally cannot** — that the cascade actually RETRIEVES (folder → boards/timelines/pages, sublist-of-a-sublist, a page's Todo mirror), that it stops at the folder boundary (a sibling folder in the same workspace stays private), that an item added later is included and one moved out is dropped, and that an invitee who is a member of NO workspace can genuinely POST a task to the shared board over HTTP.
- Known V1 gaps: realtime for cross-workspace shared items is the refetch model above, not live SSE; a folder invitee may create items in the folder but cannot rename/delete/re-share the folder itself (metadata stays owner-only, per the model above); `UpcomingTimelineWidget` drops the active-workspace filter whenever it is folder-scoped, since a folder is already a precise scope and a shared folder's workspace is one the viewer isn't in.

### Graph Layer (generic edges between any two entities, plus traversal, UI, and inline linking)

A generic system for representing arbitrary relationships between entities — "this task blocks that milestone", "this markdown page tracks that board" — as real, queryable, backlink-capable edges, independent of any one feature's hand-rolled linking column. It now spans the full stack: node registry + edges + CRUD API (below), multi-hop traversal + metrics + a dedicated `/api/graph` API, a frontend graph canvas UI (`/graph`), and inline `[[type:id|Label]]` link tokens typed directly into notes/markdown. The Knowledge Layer and Agent Runtime (their own sections below) are built on top of it. The 5 pre-existing hard-linking mechanisms (sublists, task↔list links, the markdown-page Todo sync, and the two attachment tables) are **unchanged and remain the source of truth**; the Graph Layer additionally mirrors them as `origin = 'system'` edges (Phase R1 of an ongoing rolling refactor — see `DEPRECATIONS.md` for the full phase table and the gated column-drop plan) without touching their existing columns, tables, or behavior.

- **SRN ("Solytiq Resource Name")** — the canonical textual reference for a linkable entity: `srn:{entityType}:{entityId}[#{blockId}]` (e.g. `srn:list:list_7f3a9c21`, `srn:task:1751293847221`, `srn:markdownList:md_a91c#blk_h2_intro`). `entityType` is one of `task｜list｜markdownList｜timeline｜milestone｜meeting｜folder｜file｜section｜gpsFile` — deliberately NOT `workspace`, which is a container, not a graph node. `entityId` is always the id **as a string** (bridges `tasks.id BIGINT` vs everyone else's `VARCHAR(100)`). Parse/format helpers: `backend/src/graph/srn.ts` and its mirror `frontend/src/utils/srn.ts` (kept in sync by hand — no codegen).
- **`entity_index`** is the canonical node registry — one row per linkable entity across the 10 source tables, kept in sync by AFTER-INSERT/UPDATE/DELETE DB triggers (`sync_entity_index()` in `runMigrations()`, bound per-table via a trigger argument; `sections`/`milestones` get their own join-based trigger variants since their workspace/owner must be resolved via their parent list/timeline). This is what makes edges possible despite the ID-type split described above: **`entity_links` carries a real composite FK to `entity_index` on both endpoints** (`ON DELETE CASCADE`), so deleting an entity automatically cascades away every edge touching it — no orphaned edges, no application-level cleanup code. Read only via `backend/src/graph/entityIndex.ts` (`getEntityIndexEntry`/`resolveRefs`/`searchEntityIndex`), never queried directly from a route.
- **The visibility boundary (`backend/src/graph/visibility.ts`) is the single read/write gate every Graph Layer query goes through** — no route or module may query `entity_index`/`entity_links` directly without it. `isEntityVisible()` mirrors the in-app read boundary (owner, workspace member, public workspace, or an `item_shares` invite) so the graph never shows more than the app itself would; `canWriteEntity()` additionally requires ownership/admin, or — for the three item-shareable types (`list`/`timeline`/`markdownList`) — a full-collaborator invite. Every read is existence-safe: an entity the caller can't see 404s exactly like one that doesn't exist, never leaking which is true.
- **`entity_links`** (edges) are directed, with the inverse relationship declared on the link type rather than stored as a second row — e.g. `child_of`'s inverse is `parent_of`; a handful of types (`relates_to`) are `symmetric`, and for those a `trg_links_normalize` DB trigger canonically orders `(src, dst)` before insert so A↔B can never split into two rows. That same trigger computes `is_cross_workspace` (are the two endpoints in different workspaces?) from `entity_index`. `origin` tracks who/what created an edge (`manual` = a person, via the UI or `POST /api/links`; `inline` = parsed from a `[[type:id|Label]]` token typed into notes/markdown — see below; `system` = mirrored from a legacy hard-link column, **never user-deletable**, edits/deletes 409; `automation`/`agent` = written by an Automation Hub `ai_agent` node / Agent Runtime run). All CRUD goes through `backend/src/graph/links.ts` (`upsertLink`/`updateLink`/`deleteLink`/`deleteLinksBetween`/`getLinksBetween`/`getEntityLinks`/`getBacklinks`/`findUnlinkedMentions`) — every exported function accepts an injectable `QueryExec` (defaulting to the pool) so it composes inside a caller's transaction and is unit-testable against a mock exec with no live DB, per the established convention.
- **Link-type registry (`backend/src/graph/linkTypes.ts`)** mirrors `appsRegistry.ts`'s "catalog in code, state in DB" split: 12 system types (`references｜child_of｜links_to｜tracks｜attached_to｜blocks｜duplicates｜relates_to｜derived_from｜part_of｜scheduled_as｜documents`) each declare a `label`/`inverseKey`/`inverseLabel`/`symmetric`/`color`/`edgeStyle`/`allowedSrc`/`allowedDst` (empty allow-list = any type). A workspace can additionally define its own custom relation in `workspace_link_types` (key must start with `x_`, enforced server-side to avoid ever colliding with a future system type). `resolveLinkType()`/`listLinkTypes()` merge both.
- **Backfill (`backend/src/graph/backfill.ts`, `backfillHardLinks()`)** materializes the 5 legacy hard-link mechanisms as `origin = 'system'` edges: `tasks.linked_list_id`+`'sublist'` → `list --[child_of]--> task`, `+'link'` → `task --[links_to]--> list`, `lists.parent_task_id` → the same `child_of` (redundancy check against the above), `markdown_lists.todo_list_id` → `markdownList --[tracks]--> list`, and both `task_attachments`/`milestone_attachments` (`'linked'` rows only) → `file --[attached_to]--> task|milestone`; plus two purely structural `part_of` edges (milestone→timeline, list-task→list) hidden from any future graph view by the registry's `showInGraph: false`. Every statement is `ON CONFLICT DO NOTHING`, so `runMigrations()` re-running it on every startup converges to zero new rows after the first — see `linkMigration.test.ts`. **R2 (ongoing dual-write):** `trg_hardlink_*` DB triggers (named to sort after `entity_index_*` triggers on the same table) keep every subsequent INSERT/UPDATE on the 5 mechanisms' underlying tables in sync with `entity_links` in real time — a single DB trigger per table catches every application call site at once (routes, `templateUtil.ts`, `automationEngine.ts`, …) rather than requiring each one to remember to also write the edge. **R3 (drift verification):** `backend/src/graph/verifyMigration.ts`'s `checkDrift()`/`sweepMigrationVerification()` (nightly, registered in `index.ts`'s `start()`) compares every legacy row against its mirrored edge and tracks a consecutive-clean-days streak in `app_settings`. **R4/R5 (read-switch + column drop) are gated and not yet reached** — see `DEPRECATIONS.md` for the full two-key gate (`graph_migration_verified` + `graph_links_v2`) that must open before `runMigrations()`'s dormant drop block ever touches a legacy column.
- **`entity_graph_metrics`** tracks `degree_in`/`degree_out` (maintained incrementally by a trigger on every `entity_links` write — exact, always current) and `pagerank` (too expensive to recompute per-write, so a debounced per-workspace sweep: any workspace touched by a `link` sync_log event is marked dirty, and a 5-minute interval in `index.ts`'s `start()` recomputes it via `graph/metrics.ts`'s hand-rolled TypeScript power-iteration — no new dependency, comfortably fits in process memory at per-workspace scale).
- **Traversal (`backend/src/graph/traversal.ts`)**: `localGraphNodeIds()` (recursive, visibility-scoped BFS from an anchor entity, either direction, capped at `MAX_LOCAL_GRAPH_DEPTH` hops / 5000 visited nodes, returns `truncated: true` if the cap was hit) and a shortest-path walk (capped at `MAX_SHORTEST_PATH_DEPTH`), both using a `path` array in the underlying CTE to stay cycle-safe on symmetric/self-referential link types (`relates_to`, `blocks`). **`backend/src/graph/cache.ts`** is an in-memory LRU for full-workspace graph payloads, keyed on the workspace's current `sync_log` max `seq` — the moment any tracked mutation lands the seq advances and the cached entry is naturally stale, so there's no manual invalidation and no race window.
- **`routes/graph.ts`** (`/api/graph`, behind `graphLimiter` on top of `apiLimiter`): `GET /workspace/:workspaceId` (full cached graph payload), `GET /local/:type/:id` (traversal from one entity), `GET /path` (shortest path between two entities), `GET /orphans/:workspaceId` / `GET /hubs/:workspaceId` (nodes with zero edges / highest degree), `GET /stats/:workspaceId`, `POST /recompute/:workspaceId` (force a pagerank sweep), `GET /workspace/:workspaceId/export` (JSON/GraphML-style export), `GET /types` (link-type catalog for the UI's legend/filter). All visibility-scoped through the same `graph/visibility.ts` boundary as `routes/links.ts`.
- **`routes/canvases.ts`** (`/api/canvases`) — CRUD for `graph_canvases`, saved layouts a user curates on top of the live graph. A canvas stores ONLY positions/groups/free-text notes in `layout JSONB`; it never stores its own edges — connections drawn on a canvas are real `entity_links` rows created through the normal link API, so a canvas can never drift from the graph it's showing.
- **Frontend graph UI, "the Net" (`/graph` route, `GraphScreen.tsx`)**: the Explore tab is a full-size, always-on-screen **`NeuralGraph.tsx`** canvas — a hand-rolled SVG force simulation (`utils/forceSimulation.ts`'s dependency-free `ForceSimulation` class, driven by `hooks/useForceSimulation.ts`'s `requestAnimationFrame` loop) that continuously drifts like a living network rather than sitting on a static layout. Every node is a colored, icon-bearing dot (`nodeColor`/`nodeIcon`/`nodeSize` in `utils/graphLayout.ts`, sized by combined hierarchy + relation connection count) with hover glow/dim-neighbors and a floating tooltip; positions are written straight to SVG `transform` attributes every frame (bypassing React state) so 60fps motion never triggers a re-render. **A synthetic workspace-root node is always pinned at the world origin** (`utils/graphHierarchy.ts`'s `buildWorkspaceRootNode` — `type: 'workspace'`, not a real backend entity type, never sent to the server) with every other node connected up to it through a client-computed structural hierarchy — task → section → board → folder → workspace, timeline/markdown-page → folder-or-workspace, milestone → timeline — resolved by `buildParentIndex`/`buildRenderedHierarchy` from data the app already has loaded (`hooks/useGraphHierarchy.ts` reads `useAppStore`'s lists/folders/timelines + `useMarkdownListsStore`), walking up to the nearest still-rendered ancestor when a filter hides an intermediate level so no node ever ends up visually disconnected. Two containment edges override the generic folder-or-workspace fallback: a sublist (`lists.parent_task_id`) nests under the task that owns it rather than its own (typically unset) folder, and a markdown page's auto-managed Todo list (`markdown_lists.todo_list_id`) nests under the page itself rather than the workspace/folder its list row carries — both chase to whatever ancestor those, in turn, resolve to, so a sublist-of-a-sublist (e.g. one created inside a markdown page's Todo list) chains all the way through task → Todo list → markdown page → workspace instead of short-circuiting to the root. This hierarchy is deliberately NOT stored as `entity_links` rows (see the Backfill bullet above on why `part_of` stays a narrow, hidden mirror) — it's a pure rendering-layer concern layered on top of real relations, which are drawn as a second, more prominent edge class. Above `SIGMA_THRESHOLD_NODES` (300), Explore falls back to the WebGL **sigma.js + graphology** renderer (`components/graph/SigmaGraph.tsx`) for graphs too large for a React/SVG-managed DOM to stay smooth; both `NeuralGraph` and `SigmaGraph` are lazy-loaded via `React.lazy()` so neither grows the main bundle for users who never open `/graph`. A floating **`GraphToolbar.tsx`** (search via `useEntitySearch`/`LinkPicker`, a `GraphControls.tsx` filters dropdown, Reset layout) sits top-right over the canvas; `NodeInspector.tsx` (selected node's details + its edges) floats as an overlay panel rather than pushing the canvas into a sidebar, and custom zoom-in/zoom-out/center buttons (styled to match the app, not a library's defaults) sit bottom-**left** — deliberately not bottom-right, which collides with the global AI Assistant bubble fixed at `bottom:30/right:30`. `useGraphStore.ts` owns the loaded payload, active filters, and selection; `filters.showOrphans` now defaults to **true** (the hierarchy means nothing is a true structural orphan anymore — the toggle now means "include items with no explicit relation, only the hierarchy connection"). Dragging a node pins it (`ForceSimulation.pin`/`unpin`, persisted via `useUserPrefsStore`'s `graphNodePositions`, same as before); the Canvas tab's authoring surface still uses React Flow directly (`components/graph/FlowGraph.tsx`'s `EntityNode`, wired into a `RF_NODE_TYPES` map that `GraphScreen` owns at module scope, restyled to the same dot language) since drag/pan/connect-to-link authoring fits XYFlow better than a force sim. `GraphMiniMap.tsx` (Dashboard's small live preview) and the editor-embedded `components/graph/RelationsPanel.tsx`/`BacklinksPanel.tsx` are unchanged. **Sol is Net-aware**: `useAIStore.ts`'s `buildContext()` adds a `'graph'` view (item/relation counts, top-connected items, active filters) whenever `pathname` starts with `/graph`, `buildSystemPrompt()` explains the hierarchy-vs-relation distinction and points at the shared Graph Layer tools (`search_graph`/`get_entity_links`/`get_backlinks`/`create_link`/`delete_link`, always available), and `buildTools()` adds three client-only tools — `focus_graph_node` (pan/select), `set_graph_filters`, `reset_graph_view` — executed in `components/AIAssistant/index.tsx`'s `executeTool` directly against `useGraphStore`/`useUserPrefsStore`.
- **Net readability — spacing and labels (why the Net doesn't clump)**: two rendering-layer rules keep a big graph legible, both pure and unit-tested rather than tuned by eye. (1) **Spacing** — `utils/graphLayout.ts`'s `hierarchyLinkDistance()` derives each parent→child spring's rest length from the parent's *sibling count* (arc length per child) and spills past `MAX_PER_SHELL` into further concentric shells, so on-screen density stays roughly constant whether a parent has 3 children or 300. A single fixed rest length pulled every sibling set onto the same small circle, which is what collapsed a hub like a Knowledge Base with a hundred terms into an unreadable knot. Reinforcing that, `utils/forceSimulation.ts` floors repulsion at `REPULSION_ALPHA_FLOOR` instead of scaling it fully by alpha (the springs never cool, so a fully-cooled repulsion left the springs as the only vote and the layout slowly re-collapsed after settling), keeps overlap resolution entirely unscaled as a *constraint* rather than a force, honors a per-node `collisionRadius` wider than the dot so labels have room, and golden-angle-fans a new sibling set on seed instead of heaping it on one spot. (2) **Labels** — `utils/graphLabels.ts`'s `planLabels()` decides every label's size and visibility per frame in SCREEN space: counter-scaled by `1/k` so on-screen size is constant at any zoom, then greedily occlusion-culled against each other over a coarse grid, highest-priority first (root, then focus + its neighbours, then best-connected). Zoom out and only the hubs stay labelled; zoom in and the rest fade in as room opens up — no fixed world-space font size can be both legible when zoomed out and non-overlapping when zoomed in. A dimmed (non-highlighted) node drops its label entirely rather than fading it, since a ghosted label still occupies the pixels the focused neighbourhood needs. `NeuralGraph.tsx` only *applies* both results — it runs the label pass imperatively every `LABEL_PASS_INTERVAL` frames off the same RAF loop as node positions, so neither ever triggers a React re-render.
- **Inline `[[...]]` links (`backend/src/graph/inlineLinks.ts`)**: typing `[[` inside a `NotesEditor` (task/milestone notes) or a Markdown Page block triggers `frontend/src/utils/linkTrigger.ts`'s caret/token detection, opening a `LinkPicker` (`components/LinkPicker.tsx`, presentational — takes `results`/`loading`/`query`/`activeIndex`/`onPick`/`onHover`) backed by `useEntitySearch.ts` ← `GET /api/links/search` (`searchEntityIndex`, visibility-scoped). Picking an entity inserts an **ID-anchored** token, `[[type:id|Label]]` (e.g. `[[task:1751293847221|Ship the release]]`) — the id, not the display label, is authoritative, so a later rename never breaks the link. On save, `syncInlineLinksForText`/`syncInlineLinksForBlocks` (wired into `routes/lists.ts`, `routes/markdownLists.ts`, `routes/timelines.ts`, `routes/meetings.ts` at every content-save site) parse the current text, diff against the previously-stored token set for that field, and write/remove `origin = 'inline'` edges for exactly what changed — mirroring `mentions.ts`'s diff-and-notify pattern so a re-save never duplicates or churns edges. Rendered inline as an `EntityChip.tsx` (`components/EntityChip.tsx`) — emoji/icon + title, colored by entity type, clickable to navigate.
- **`routes/links.ts`** (`/api/links`, behind both `apiLimiter` and a dedicated `linksLimiter`): `GET /` (filter by `src`/`dst`/`type`/`direction`), `GET /entity/:type/:id` (all edges grouped by link type), `GET /entity/:type/:id/backlinks`, `GET /entity/:type/:id/unlinked` (a **title-substring heuristic** — real content-mention parsing from `[[...]]` tokens is now handled separately, see Inline Links above; this endpoint remains a lighter-weight suggestion heuristic, not superseded by it), `GET /search` (entity search backing the `[[...]]` picker and the graph UI's node search — `searchEntityIndex`), `POST /` and `POST /batch` (≤100 edges, one transaction), `PATCH /:id`/`DELETE /:id` (props/weight only — endpoints and link type are immutable, delete+recreate instead; both 409 on `origin = 'system'`), and `GET/POST /types` + `DELETE /types/:id` for custom types. Creating an edge requires write access to the **source** and read access to the **destination** (asymmetric by design — referencing something you can read is not an edit to it).
- `link` is a SIGNAL sync entity (`sync_log`, `SIGNAL_ENTITIES` in `routes/sync.ts`) — edge mutations push a refetch signal that `GraphScreen`/`useGraphStore` consume to refresh the canvas live.
- **Known V1 gaps (tracked, not yet resolved):** no typed-relation picker UI beyond the link-type dropdown (no visual relation-type legend editor); the legacy hard-link columns have not been dropped — see `DEPRECATIONS.md` for the exact two-key gate and why drift-verification alone is deliberately insufficient to trigger it; both attachment tables (`task_attachments`/`milestone_attachments`) keep their own physical-file columns and are explicitly out of scope for any future column drop, even once the gate opens, since `entity_links`/`entity_attachments` don't replace their `file_path`/`mime_type`/etc. storage.

### Knowledge Layer (hybrid search / RAG)

Full-text semantic search over everything in the Graph Layer's `entity_index`, built on top of it: `backend/src/knowledge/` chunks each entity's text content, optionally embeds it, and serves hybrid lexical+vector search scoped through the exact same visibility boundary as the rest of the Graph Layer.

- **Chunking (`knowledge/chunker.ts`)**: pure, dependency-free, side-effect-free text splitting — `chunkText()` splits on blank-line paragraph boundaries (never a fixed-size sliding window) up to ~2000 chars per chunk, hard-splitting on word boundaries only when a single paragraph exceeds that. Per-entity-type text extraction (task notes, markdown page blocks flattened via `flattenMarkdownBlocks`, milestone notes, etc.) feeds this. Each chunk's `content_hash` (SHA-256) means an unchanged paragraph is never re-chunked or re-embedded on a later sweep — only genuinely edited text does work.
- **`entity_chunks`** (see Core Data Model) stores the chunks; **`embedding_queue`** is the work list an entity is placed on whenever its extracted text changes. **`knowledge/embeddingWorker.ts`**'s `sweepEmbeddingQueue()` (2-minute interval, registered in `index.ts`'s `start()`) drains pending rows, calls the configured embedding provider, and writes `entity_chunks.embedding`.
- **pgvector is optional, not required.** `runMigrations()` attempts `CREATE EXTENSION IF NOT EXISTS "vector"` and degrades gracefully on failure (`knowledge/state.ts`'s `isPgvectorAvailable()` gate, checked before any embedding read/write) — a plain `postgres:16` image works fine, just lexical-only. `docker-compose.yml` uses the `pgvector/pgvector:pg16` image so semantic search is enabled by default in the shipped stack. Embeddings are fixed at 1536 dimensions (`EMBEDDING_DIMENSIONS`, matching OpenAI's `text-embedding-3-small` and comparable small models) with an HNSW cosine index — chosen over IVFFlat because it needs no training data and builds incrementally, which matters for a table that starts empty on every fresh install. A `gin_trgm_ops` trigram index on `content` always exists regardless of pgvector, so lexical search never depends on it.
- **`knowledge/embedProvider.ts`** calls the same OpenRouter-compatible endpoint convention as the rest of the AI stack (admin-configurable model/key via `app_settings`); when unset, `embedTexts()` is a no-op and search runs lexical-only automatically — no separate feature flag to keep in sync.
- **Hybrid search + graph boost (`knowledge/fusion.ts` + `knowledge/search.ts`)**: `searchKnowledge()` runs a trigram-lexical query and (when available) a pgvector cosine-similarity query over `entity_chunks`, fuses the two rankings with **Reciprocal Rank Fusion** (rank position, not raw score, since the two retrieval methods' scores aren't on comparable scales — `k=60`, the standard smoothing constant from the original RRF paper), then re-ranks with a bounded boost from each hit's `entity_graph_metrics.pagerank` (`applyGraphBoost`) — a well-connected entity nudges up over an equally-lexically-relevant orphan, without ever letting pagerank alone dominate the ranking. Every query joins through `graph/visibility.ts`'s `visibleCondition` — a chunk on an entity the caller can't see never surfaces, full stop.
- **`routes/knowledge.ts`** (`/api/knowledge`, behind `knowledgeLimiter`): `POST /search` (the query endpoint — `CommandPalette.tsx` surfaces results in a dedicated group), `GET /status` (pgvector availability, queue depth, embedding config presence), `POST /reindex` (admin-only — re-enqueues everything). Admin-configurable settings (`GET`/`PUT`) live under `routes/admin.ts` alongside the other `app_settings` keys, surfaced in `SettingsScreen.tsx`'s **Knowledge Search** admin section.
- **Soft monthly token budget**: embedding calls are metered the same way OpenRouter chat calls are (`ai_usage`-style tracking) so a runaway reindex can't produce an unbounded provider bill; exceeding the budget pauses new embedding work without failing existing search (lexical fallback still serves results).
- **Known V1 gaps**: no chunk-level citation UI yet (search results link to the source entity, not a highlighted excerpt in-place); re-ranking uses a single graph-boost signal, not a learned re-ranker.

### Knowledge Base (the per-workspace curated dictionary)

Exactly **one Knowledge Base per workspace**, added from the Sidebar's Add button and **always pinned at the top of the sidebar** above every folder, board, page and timeline. It is the workspace's dictionary — the terms, people, projects and systems that workspace actually talks about — and its whole purpose is to be the thing Sol, the Agent Runtime and any connected MCP client look a term up in **instead of guessing at it**.

**Not to be confused with the Knowledge LAYER above.** That is fuzzy retrieval (chunking, embeddings, RRF) over content people wrote for other reasons; this is the terms people wrote down *on purpose*. They are complementary and deliberately named apart in code — `backend/src/knowledgeBase/` + `/api/knowledge-base` vs `backend/src/knowledge/` + `/api/knowledge` — so no future reader has to disambiguate two things called "knowledge". Entries still flow **into** the Knowledge Layer (one `case` in `embeddingWorker.ts`'s `fetchDocumentText`, term and aliases leading the indexed text since that is its highest-signal part), so `knowledge_search` surfaces curated definitions alongside everything else.

- **One base per workspace is a DB constraint** (`knowledge_bases.workspace_id UNIQUE`), not an application check. `createBase()` returns the EXISTING base rather than erroring on a double-create, so two tabs racing the sidebar's add button converge on one base instead of one of them failing.
- **Both types are first-class Graph Layer citizens.** `knowledgeBase` and `knowledgeEntry` are real `ENTITY_TYPES` with `entity_index` triggers (`knowledgeBase` via the generic `sync_entity_index()` CASE; `knowledgeEntry` via its own join-based variant, since an entry inherits its workspace from its parent base exactly as sections/milestones do). That single registration buys the Net, entity search, backlinks, the `[[...]]` picker and the CommandPalette with no bespoke code.
- **Relations reuse `entity_links` verbatim** — no new edge machinery. Four new SYSTEM link types (`defines`, `synonym_of` (symmetric), `broader_than`/`narrower_than`, and the structural `entry_of` with `showInGraph: false`). These are system rather than per-workspace `x_` types on purpose: a lookup that walks broader/narrower has to mean the same thing in every workspace for the AI-facing dictionary to be portable across them. **Typing `[[type:id|Label]]` in a definition creates a real edge via the existing `syncInlineLinksForBlocks`** — authoring a definition draws the graph as a side effect, which is the highest-value reuse in the design.
- **Entry bodies are the SAME block shape a Markdown Page uses** and are edited by the SAME component: `components/markdown/BlockEditor.tsx`, extracted out of `MarkdownListScreen.tsx` (which dropped from 1340 to ~350 lines in the process). The editor is **controlled and persistence-agnostic** — it reports a new block list and the host decides what saving means, which is what lets a Markdown Page save through its version-checked `PUT` while an entry saves through a different endpoint with no branching in the editor. Image storage is likewise **injected** (`imageUrl`/`uploadImage`), because the two hosts own images under different `markdown_list_images` owners (see the polymorphic `owner_type`/`owner_id`). Block constructors live in `utils/markdownBlocks.ts` — hosts need `makeEmptyBlock` before the editor mounts, and a file exporting both a component and plain functions breaks Fast Refresh.
- **`knowledgeBase/blocks.ts` deliberately does NOT run todo reconciliation.** A Markdown Page mirrors its `/todo` blocks into a real auto-managed list because a page is where work gets tracked; a definition is not, and mirroring its checkboxes would manufacture phantom work items out of documentation. A `/todo` block still renders and toggles — it just stays local. Everything else (inline-link sync, `@`-mention notifications, embedding enqueue) runs exactly as it does for a page.
- **Term lookup is exactness-first, never fuzzy** (`knowledgeBase/lookup.ts`): exact term → exact alias → **no definition**, plus near-miss suggestions labelled as such. This is the core design decision of the feature. When a model is about to state a fact about the user's own vocabulary, a ranked guess that is 60% right is worse than a clean miss, so `lookupTerm()` never silently degrades into similarity matching. `listGlossary()` returns terms + aliases + summaries with **no bodies** — small enough to carry on every AI turn.
- **The UI is net-first** (`/knowledge`, `KnowledgeScreen.tsx`): the base is the pinned centre (the same role the synthetic workspace node plays on the main Net — `buildRenderedHierarchy` now takes an explicit root SRN so both cases share one builder), every term orbits it, and clicking a term opens `EntryInspector` as an **overlay** rather than pushing the canvas aside. Edges drawn here are always real `entity_links`, never canvas-only lines — the same invariant `graph_canvases` holds — and a board referenced by a definition renders nested *under* the term that references it. The sidebar row sits **outside the drag/reorder logic entirely**: there is one base per workspace, it has no `position` to sort by, and it can never be dragged into a folder — which is why "always at the top" needed no position math.
- **Access:** READ for anyone who can access the workspace; WRITE for any workspace **member** (a workspace has one shared base, so owner-only writes would lock every other member out of the feature's whole point — `graph/visibility.ts`'s `canWriteEntity` carries the matching exception for the two `knowledge*` types); DELETE THE BASE only for the workspace owner or an instance admin, since it cascades every entry. There is no Trash bucket for a Knowledge Base — deleting it is an explicit, confirmed act, not the kind of accidental delete the trash tables exist to soften.
- **Suggest-only extraction** (`knowledgeBase/extract.ts`): a "Find concepts" button scans workspace content and proposes candidate terms for a human to accept. The candidate finder is a **deterministic heuristic** (acronyms + capitalized phrases of up to three words, seen at least twice), NOT an LLM sweep — it costs nothing, runs the same way twice, and is unit-testable as a pure function. An always-on extraction sweep was considered and rejected: it spends provider budget continuously and fills the base with unvetted noise. **Nothing is visible to the AI until accepted.** Re-running converges via `ON CONFLICT`; a rejected suggestion is kept so the same term isn't proposed forever.
- **Known V1 gaps:** no per-entry emoji/colour picker in the inspector yet (the fields exist and round-trip, but are only settable through the API); `properties JSONB` round-trips and is surfaced to the AI but has no key/value grid in the UI yet; the concept scan is title/body heuristics only and does not consider the graph.

### Agent Runtime (autonomous / assisted AI agent)

A per-workspace AI agent that can actually *act* — not just answer questions — by calling the exact same shared tool registry (`aiTools.ts`) the internal "Sol" assistant and the MCP server use, wrapped with an explicit policy engine, human-approval gating, and curated revert.

- **Modes (`workspaces.agent_mode`)**: `off` (default — the agent never runs), `suggest` (every tool call becomes an `agent_proposals` row awaiting human accept/reject, nothing executes automatically), `assisted` (tools listed in the workspace's `agent_policy.autoApproveTools` run immediately; everything else still proposes), `autonomous` (runs everything the policy allows without asking, up to its run limits). Configured per-workspace in a new **Agent** tab of `WorkspaceSettingsModal.tsx` (owner-only), backed by `PATCH /api/workspaces/:id/agent`.
- **Policy (`agent/policy.ts`, `workspaces.agent_policy JSONB`)**: pure, side-effect-free decision logic — `parseAgentPolicy()` merges a possibly-partial stored policy over `DEFAULT_AGENT_POLICY` (never trusts JSONB shape blindly), then `canUseTool()`/`needsApproval()`/`exceedsRunLimits()` decide, for each tool call in turn, whether it's allowed at all (`allowedTools`/`deniedTools` allow-list/deny-list), whether it can auto-run or must propose (`autoApproveTools`, plus `requireApprovalOver` thresholds — `deleteAny` defaults **ON**, so any delete-shaped tool call proposes unless a workspace owner explicitly relaxes it), and whether the run has hit its `maxActionsPerRun`/`maxToolCallsPerRun`/`dailyTokenBudget` caps. `runtime.ts` is the only caller that enforces these decisions — the policy module itself makes no DB or HTTP calls, which is what makes it unit-testable with zero mocking (`agentPolicy.test.ts`).
- **Execution (`agent/runtime.ts`)**: `startAgentRun()` inserts an `agent_runs` row and returns its id immediately — the loop itself runs fire-and-forget (`void ...catch()`, the same pattern `automationEngine.ts`'s `runAutomation()` uses, for the same reason: an HTTP request shouldn't block on a multi-turn LLM tool-calling loop). Each turn: call the model with `getOpenRouterToolDefs()` (the same defs Sol gets, **minus** any `mcpOnly`-flagged tool — see Shared AI Tool Registry), run every requested tool call through the policy checks above, execute (`executeAiTool`) or record a proposal, snapshot revertible state (`agent/inverse.ts`) around tools that support it, and append an `AgentRunStep` to `agent_runs.steps`. A run can be started manually (`POST /api/agent/runs`), from the Dashboard's **Agent Inbox** (`AgentInbox.tsx`, surfaced in `DashboardScreen.tsx` — pending proposals across workspaces, with accept/reject actions calling `POST /api/agent/proposals/:id/accept|reject`), or from an Automation Hub `ai_agent` action node (see Automation Hub) — every entry point funnels through the same `startAgentRun()`.
- **Curated revert (`agent/inverse.ts`)**: **deliberately not** a generic "undo anything the agent did" system — building one across `aiTools.ts`'s 40+ handlers would require every one of them to report structured before/after state, and most only return a human-readable summary string. Instead, a small, explicit `REVERTIBLE_TOOLS` table snapshots the state it needs directly (via the same tables the tool itself touches) around a curated subset of tools where doing so is straightforward and correct; every other tool call is recorded as simply not revertible — visible in the run trace, never silently wrong. `POST /api/agent/runs/:id/revert` walks that run's `agent_mutations` rows in reverse and restores each `before_state` (null `before_state` = the mutation was a create, so revert deletes it). Extending coverage later means adding one more snapshot/apply pair to `REVERTIBLE_TOOLS`; the runtime loop, `agent_mutations` table, and revert endpoint are already fully general.
- **`routes/agent.ts`** (`/api/agent`, behind `agentLimiter`): `GET`/`POST /runs`, `GET /runs/:id`, `POST /runs/:id/cancel`, `POST /runs/:id/revert`, `GET /proposals`, `POST /proposals/:id/accept|reject`. Proposals carry a 7-day `expires_at`, swept hourly (`sweepExpiredProposals`, registered in `index.ts`'s `start()`) — an unactioned proposal quietly expires rather than lingering forever.
- **`assign-agent` (`routes/tasks.ts`, `POST /api/tasks/:id/assign-agent`)**: a lightweight per-task entry point that starts a run scoped to "complete/help with this task," reusing the same `startAgentRun()` path as every other trigger.
- **Notifications**: an agent run that produces a proposal or finishes notifies the relevant user (`NotificationType` extended with agent-run/proposal variants in `notifications.ts`), following the same best-effort, never-breaks-the-triggering-call convention as every other notification source.
- **`useAgentStore.ts`** (frontend) holds proposals/run state for the Agent Inbox; `Workspace.agentMode`/`agentPolicy` (types.ts) round-trip the workspace settings.
- **Security**: an agent run can only ever do what the shared tool registry already scopes it to (`userId`-bound queries, no cross-user reach — see Shared AI Tool Registry's security invariant), further narrowed by its own workspace's policy. It **cannot** call any of the 6 Agent Runtime meta-tools (`start_agent_run`, `get_agent_run`, `list_agent_runs`, `list_agent_proposals`, `accept_agent_proposal`, `reject_agent_proposal`) on itself — those are flagged `mcpOnly: true` and excluded from `getOpenRouterToolDefs()` specifically to close an unbounded self-fork risk; see `DEPRECATIONS.md`'s "MCP tool visibility" note for why removing that flag would need a real recursion-depth guard first.

### Real-time Sync (SSE)

- `sse.ts` keeps an in-memory registry of connected clients per user. Mutating endpoints call `broadcastToUser(userId, channel)` (channels like `'lists'`, `'files'`, `'timelines'`) to push a refresh signal.
- The frontend opens `GET /api/events` (EventSource) via `connectSSE()` in `client.ts`; stores listen and reload the affected data. Heartbeat pings every 25s keep the connection alive behind Nginx.

### Public Sharing (files, lists, timelines)

Public share endpoints are mounted **directly in `index.ts`** (not behind `verifyToken`):

- **Files:** `GET /api/share/:token` (metadata) and `GET /api/share/:token/download` (binary; optional `?password=`).
- **Lists:** `GET /api/share/list/:token` (metadata) and `GET /api/share/list/:token/content` (sections + tasks; optional `?password=`).
- **Timelines:** `GET /api/share/timeline/:token` (metadata) and `GET /api/share/timeline/:token/content` (milestones; optional `?password=`).

Sharing model for lists/timelines (distinct from the workspace `is_public` flag — see Key Architectural Decisions):
- An **opaque `share_token`** (24-byte hex) is minted when sharing is first enabled. `share_enabled` toggles the public link; `share_password_hash` and `share_expires_at` are optional (full parity with file shares).
- **Owner-side management:** `PUT /api/lists/:listId/share` and `PUT /api/timelines/:timelineId/share` toggle/configure the link.
- **Subpages:** lists have `share_subpages`. When enabled together with sharing, the share state cascades to nested sublist descendants (each gets its own token, inheriting password/expiry). The list-content endpoint exposes each shared sublist's token as `linkedShareToken` so the public page can deep-link to the subpage, plus a `linkedProgress` summary for the ring indicator. When a sublist isn't live-shared, its token is omitted.
- **Shared view mode (lists only):** `lists.share_view_mode` (`'list'｜'kanban'｜'timeline'`, nullable) independently overrides which of the Board screen's three layouts (see Board Screen: List vs Kanban vs Timeline View) the *public* page renders — separate from the owner's own `view_mode`, so a list can be browsed as Kanban in-app while its share link shows a Timeline, or vice versa. `PUT /:listId/share`'s `viewMode` field sets it explicitly (omit = unchanged); both `GET /api/share/list/:token` and `/content` resolve and return the effective value as `viewMode` (`share_view_mode` falling back to `view_mode`, clamped to a valid mode — see `resolveListViewMode()` in `index.ts`). The content endpoint also includes each task's `createdAt`/`completedAt` (needed by the Timeline renderer). `SharedListPage.tsx` picks the List/Kanban/Timeline read-only renderer purely from this resolved `viewMode` — there is no visitor-facing switcher, matching the "one link, one view" model. The read-only Kanban/Timeline components live in `frontend/src/components/SharedListViews.tsx` (`SharedKanbanView`, `SharedTaskTimelineView`, plus the shared `SharedTaskRow` used by both List and Kanban) — adapted from the authenticated Kanban block and `TaskTimelineView.tsx` but with all editing, dragging, and mutation affordances stripped, so a public visitor can see structure/status/dates but never modify anything.
- Expired or disabled links return `410`/`404`; private/missing return `404`.

### File Uploads

- Handled by `multer` in `routes/files.ts`. Files saved to disk under `UPLOAD_DIR`.
- Max upload size: 200 MB (multer config). Nginx proxy limit: 210 MB.
- Each user has a 15 GB storage quota enforced server-side (configurable via `app_settings.storage_quota_per_user`).
- File sharing uses an opaque `share_token` (hex). Public file info and download are at `/api/share/:token` and `/api/share/:token/download`.
- **Task attachments** (`taskAttachments.ts`) either upload a new file or link an existing `shared_files` row to a task. **Milestone attachments** (`milestoneAttachments.ts`, mounted at `/api/timelines/milestones/:milestoneId/attachments`) mirror this for timeline milestones; access is gated by the milestone's timeline (owner, or workspace-public for reads).

### GPS / Route Planner

- `routes/gps.ts` + `gpx.ts` handle GPX and FIT files. Parsing uses `fast-xml-parser` (GPX) and `fit-file-parser` (FIT); track smoothing/decimation uses `simplify-js`.
- Endpoints under `/api/gps`: list, `upload`, `:id/data`, `:id/smooth(+-save)`, `:id/rename`, `new`, `combine`, `:id/download`, `:id/points`, `:id/route-state`, delete, plus `route` (Valhalla snapping/routing) and `pois` (Overpass POI search).
- **Route Planner State v1** (`route_state JSONB`) stores rich editing state — control points, routed/offgrid spans, POI markers, course points — alongside the canonical track. See `GpsRouteStateV1` and related types in `types.ts`.

### Templates

- **`templates` table** stores a user-owned, workspace-agnostic snapshot of a list's or timeline's full structure (`type`, `name`, `description`, `emoji`/`color`/`color_bg`, `is_shared`, `structure JSONB`). `is_shared` is a simple public toggle — not a share link — that makes the template visible (read-only for non-owners) to every other user of this instance.
- **`backend/src/templateUtil.ts`** builds/consumes the `structure` tree: `captureListStructure`/`captureTimelineStructure` read an existing list/timeline (recursively for owned sublists) into a template node; `instantiateListStructure`/`instantiateTimelineStructure` materialize a brand-new list/timeline (recursively for sublists) inside one transaction.
  - **Dates are relative:** every captured deadline/milestone date becomes a whole-day offset from "today" at capture time (`daysBetween`/`addDaysISO`), resolved back against "today" on instantiation — a template stays meaningful however long it sits before reuse.
  - **Sublists are fully supported:** a task linking to an owned child list (`linked_list_type = 'sublist'`) recursively captures/recreates that list's own sections/tasks. A `'link'` reference to an unrelated standalone list is dropped (kept as a plain task) rather than pulling in a whole separate list. `lists.parent_task_id` has an FK to `tasks(id)`, so a recreated sublist is always inserted with `parent_task_id = NULL` and only backfilled via `UPDATE` once its linking task exists.
  - **Attachments carry over owner-only:** only `'linked'`-type attachments (which reference a durable, independently-owned `shared_files` row — safe to reference from more than one attachment row) are captured; `'upload'`-type attachments are skipped (they're 1:1 with their physical file, so a second reference would risk a dangling file on delete). Captured attachments are only re-linked when the instantiating user is the template's owner; a shared/public template used by someone else never carries attachments. The referenced file is re-verified to still exist and be owned by that user at instantiation time.
  - Generated task ids use a per-request BigInt-based counter (`makeTaskIdGenerator`) rather than `Date.now()`-based jitter, so bulk-creating many tasks in one transaction can't collide.
- **`routes/templates.ts`** (`/api/templates`): `GET /` (own + every shared template, optional `?type=list|timeline`), `POST /` (capture from a list/timeline you own), `PUT /:id`/`DELETE /:id` (metadata only — owner or admin), `POST /:id/use` (instantiate; body: `name`, `isPublic`, `workspaceId`, `folderId`). A private template you don't own 404s rather than 403s (existence isn't leaked).
- Frontend: the **Templates** sidebar nav item (below the workspace switcher, workspace-agnostic) opens `/templates` (`TemplatesScreen.tsx`) to create/browse/share/delete templates. `AddWizard` inserts a template-select step (`TemplateSelectStep.tsx` → `UseTemplateModal.tsx`) between choosing List/Timeline and the classic blank-creation wizard.

### Automation Hub

Flow-chart-style automations (e.g. "delete a task once it's checked" or "archive a list once everything on it is done"). Gated behind the **App Directory** (`appsRegistry.ts` — must be installed instance-wide via Settings → System → Discover Apps before `/api/automations` appears at all, same `requireAppInstalled('automations')` gate as `gps`/`files`/`mcp`).

- **Attached to one Board/Page/Timeline, not browsable workspace-wide.** There is no Sidebar nav item and no standalone gallery route reachable by navigation — the only entry point is a small **⚡ Automations** button (`components/AutomationsButton.tsx`, hidden unless the app is installed) at the top-right of `ListScreen`/`MarkdownListScreen`/`TimelineScreen`, which opens `AutomationsScreen.tsx` filtered to that one item (`/automations?ownerType=list|timeline|markdownList&ownerId=…`). Every automation carries `owner_entity_type`/`owner_entity_id` (nullable, backfilled from `trigger_scope.listId` for pre-existing rows — a `schedule`-triggered automation from before this column existed has no natural single owner and is simply not reachable from any item's button anymore, though it keeps running). `POST /api/automations` requires `ownerEntityType`+`ownerEntityId` and **derives `workspace_id` from that entity** (`resolveOwnerEntityWorkspace()` in `routes/automations.ts`) rather than trusting an independent client-supplied `workspaceId` — a client can no longer create an automation whose stored workspace disagrees with the item it's attached to. `GET /api/automations?ownerType=&ownerId=` lists only that item's automations (workspace membership is still the access check — an item-share invitee with no workspace membership does **not** gain automation access, deliberately unchanged from the workspace-scoped model this replaced). `AutomationEditorScreen.tsx`'s "back"/"Cancel" navigation resolves to the owning item's own route (`ownerEntityPath()`, exported from `AutomationsScreen.tsx`) — `/list/:id`, `/timeline/:id`, or `/markdown-list/:id` — never a gallery page.
- **This is a UI/discovery scoping change only — every IDOR guard and execution path below is untouched.** `automationGraph.ts`'s `assertGraphRefsInWorkspace`/`assertGraphWorkspaceRefsAccessible`, `automationTypes.ts`'s `assertListInWorkspace`/`assertFolderInWorkspace`, and all of `automationEngine.ts` still key off `automations.workspace_id` exactly as before; an action that moves a task/list to a different list or workspace (see the consolidated List → Move node below) validates and executes identically regardless of which item the automation happens to be attached to.
- The Graph Layer's **Net** (`/graph`) lost its Sidebar nav item the same way — its only entry point is now the Dashboard's `GraphMiniMap.tsx` widget (bottom-right), which already linked to `/graph`; the route itself is unchanged.

- **V1 graphs are linear**: exactly one trigger node feeding one or more chained action nodes — no branching, no cycles. This is enforced server-side on every save by **`automationGraph.ts`**'s `normalizeAutomationGraph()` (walks the edge chain; rejects multi-trigger, branching, cycles, unknown node types, and trigger/action incompatibilities) regardless of what the client sends — the frontend editor also only ever produces this shape by construction, but the backend check is the real guarantee.
- **Node-type registry (`automationTypes.ts`)** is the single source of truth, mirroring `aiTools.ts`'s pattern: each trigger/action has a JSON-Schema-ish `paramsSchema`; actions also have a server-side `execute()` handler. V1 triggers: `task_completed`, `list_all_completed`, `task_created` (all list-scoped — dashboard tasks don't participate), `schedule` (daily/weekly, no mutation actor). V1 actions surfaced in the editor's "add action" picker: the consolidated **`task`**, **`list`**, **`folder`** nodes (see below), plus `http_request`, `code`, and **`ai_agent`** (hands a `goal` string — `{{...}}`-expression-substituted, e.g. `"Draft a project plan for {{trigger.task.title}}"` — to `agent/runtime.ts`'s `startAgentRun()` for this workspace, subject to that workspace's own `agent_mode`/`agent_policy`; a `suggest`-mode workspace queues a proposal for a human rather than acting immediately. See Agent Runtime). A `providesTask`/`providesList` vs `requiresTriggerTask`/`requiresTriggerList` compatibility matrix stops an automation from being saved if an action needs data its trigger doesn't supply (`http_request`/`code`/`ai_agent` are compatible with every trigger, including `schedule`; for `task`/`list` these flags are **functions of the node's own params** — resolved via `resolveRequirement()` — since only some of the 5 operations below need a trigger-provided task/list). There is no `notify` action — automation feedback comes from Run History (and the editor's per-node Test button — see below), not an in-app inbox.
- **Consolidated Task/List/Folder nodes**: rather than one action type per verb, a single node per entity carries an **`operation`** dropdown (`create`/`delete`/`move`/`edit`/`rename`) that switches which of the node's fields apply — a field's `showIf: {param, equals}` hint (evaluated by the editor's `ParamsForm`, and mirrored in `validateClientSide`) hides everything irrelevant to the chosen operation. Each operation **delegates to the pre-existing granular action** of the same behavior wherever one already existed (`create_task`, `delete_task`, `move_task`, `rename_task`, `create_list`, `delete_list`, `move_list`/`move_list_to_workspace`, `rename_list`, `create_folder`, `delete_folder`, `rename_folder` — all still exported from `ACTION_REGISTRY`, just flagged `hidden: true` so the "add action" picker no longer offers them directly; an automation saved before this consolidation still resolves and runs its old node types exactly as before). The only genuinely new operations are **Task → Edit** (note/deadline/time/priority/badge, via the same actor-tagged `updateListTaskFields` the HTTP route uses — title stays under Rename; `ParamField`'s `deadline`/`time` fields reuse the exact `CalendarPicker`/`TimePicker` widgets the rest of the app uses for date/time input, keyed by `fieldKey` the same way the `schedule` trigger's own `time` field already was), **List → Edit** (archive *or unarchive*, unlike the one-way hidden `archive_list`), **List → Move**'s single form (a `targetFolderId` + `targetWorkspaceId` pair — filling in a workspace takes priority over the folder field, replacing the old two-separate-actions split), **Folder → Edit** (public/private toggle), and **Folder → Move** (folders never had a cross-workspace move before, since they can't nest — mirrors `move_list_to_workspace`'s simplified V1 semantics, cascading to the folder's lists/sublists/tasks *and* timelines). A list task's **Move**/**Create** target section (`targetSectionId`) is an `isSectionId` dropdown, not a free-text field — populated straight from the already-loaded target list's own `sections` (no extra endpoint). Param keys are deliberately reused verbatim from the granular actions (`targetListId`/`targetSectionId`/`targetFolderId`/`targetWorkspaceId`) so the existing IDOR guards below need no changes to cover the new nodes.
- **Loop prevention (`automationEngine.ts`), by construction, not a depth counter**: every mutation that can fire a trigger takes an explicit `MutationActor` (`{type:'user', userId}` or `{type:'automation', automationId, runId}`). `fireTrigger()` no-ops immediately unless `actor.type === 'user'`. The three extracted, actor-tagged mutation functions in `routes/lists.ts` (`createListTask`, `updateListTaskFields`, plus `setListArchived`/`deleteTaskRow` for the actions) are called by BOTH the HTTP routes (`user` actor) and the engine's action handlers (`automation` actor) — so an automation's own writes can never re-trigger another automation run. Grep `fireTrigger(` to audit every call site. List/folder deletes always go through the shared, exec-parameterized `softDeleteListTreeExec`/`softDeleteFolderExec` helpers (`trashUtil.ts`) so an automation's `delete_list`/`delete_folder` action lands in Trash exactly like a user-initiated delete.
- **Execution is per-step, not one all-or-nothing transaction**: `runAutomation()` walks the action chain and lets each node commit its own database writes as it runs — single-statement actions via a bare, auto-committing `ctx.exec`; any action with more than one dependent write opens its own short-lived block via `ctx.withTransaction(fn)` (a thin adapter over `db.ts`'s `withTransaction` that also forces a ROLLBACK when the wrapped action *returns* `{ok: false}`, not just when it throws — via the internal `ActionRollbackSignal`). If a later node fails, **earlier successful writes are NOT undone** — this deliberately replaces an earlier "whole run is one transaction" guarantee, since an `http_request` action's side effect can't be rolled back once sent anyway. Run History's per-step log shows exactly how far a run got. Logs to `automation_runs` (including an `is_test` flag — see Testing below) and is fired `void ...catch()` (never awaited by the request that triggered it). The `schedule` trigger isn't mutation-driven — a 5-minute `setInterval` sweep (registered in `index.ts`'s `start()`, same pattern as the AI-file-purge cron) fires anything with `next_fire_at <= NOW()`.
- **Data flow between nodes**: every node — the trigger and every action — produces a JSON `output` (`ActionResult.output`), accumulated into a per-run `nodeOutputs` map keyed by node id (seeded with the trigger's own output, via `serializeTriggerOutput()`, under its node id; the trigger itself is recorded as a synthetic first entry in `automation_runs.steps` — no separate column needed). `TriggerContext.task` carries the FULL task record (`note`/`noteMarkdown`/`deadline`/`time`/`priority`/`badge`/`sectionId`/`position`/`createdAt`/`updatedAt`, not just `id`/`title`/`listId`/`checked`) — `createListTask`/`updateListTaskFields` (`routes/lists.ts`) and the `/test` endpoint's auto-pick query both populate every field from the row they already have in hand, so `{{trigger.task.x}}` and the editor's Data panel have real, complete data to work with rather than a sparse stand-in. A later node's string params can reference any earlier node's output via a tiny, **eval-free** `{{...}}` token syntax resolved centrally in `runAutomation()` before each node's `validate`/`execute` ever sees its params (`automationExpressions.ts`): `{{trigger.task.title}}` (the trigger's own output), `{{$json.status}}` (shorthand for the immediately-preceding node), `{{nodes.<nodeId>.x}}` (any earlier node, by id). The resolver is a plain property-path walker with a strict character whitelist — no `eval`/`Function`, so a malicious-looking token can only ever fail to resolve, never execute. Per-step `output` is size-capped (~50KB, via `truncateStepForStorage`) before being persisted to `automation_runs.steps` JSONB.
- **HTTP request action (`http_request`)**: sends a request to a user-supplied URL (method/headers/query params/JSON-or-text body, all expression-substituted) using the same global-`fetch` + `AbortSignal.timeout()` convention already established for the GPS route planner's Valhalla/Overpass calls (`routes/gps.ts`) — no new HTTP client dependency. **SSRF-guarded** (`httpNode.ts`'s `assertPublicUrl`): resolves the hostname via `dns.promises.lookup` and allow-lists *only* `ipaddr.js`'s `'unicast'` range classification — fail-closed, so loopback/link-local (including the `169.254.169.254` cloud-metadata address)/private RFC1918/multicast/IPv6 unique-local are all rejected without needing to hand-enumerate bad ranges. Known, accepted V1 gap: this is a resolve-then-check-then-fetch guard, not a rebinding-proof pinned-socket implementation (a DNS answer could in principle change between the check and the request). A non-2xx HTTP response is still `ok: true` (the request completed; `output.status` carries the code) — only a network failure/timeout/SSRF-block/invalid URL fails the action.
- **Code action (`code`)**: runs user-supplied JavaScript inside a real **`isolated-vm`** V8 isolate (`codeNode.ts`) — deliberately *not* Node's built-in `vm` module, which is a well-known weak sandbox with documented escapes. The isolate gets a single global, an `input` JSON string (`{trigger, $json, nodes}` — the same shape `{{...}}` tokens resolve against) parsed inside the isolate itself, and nothing else: no `require`/`process`/filesystem/network. A 5-second CPU-time timeout catches infinite loops; a 32MB memory limit catches runaway allocations; the returned value is round-tripped through JSON so only plain, JSON-serializable data can ever leave the sandbox. The `code` param is the one param **exempt** from `{{...}}` substitution (it's raw source, not a template string). `isolated-vm` is a native module — `backend/Dockerfile` is a 3-stage build (`deps`/`builder`/runtime) so the C++ toolchain needed to compile it never ships in the final runtime image.
- **IDOR guards**: any node param naming a list (`trigger_scope.listId`, an action's `targetListId`) or folder (`targetFolderId`) must belong to the automation's own workspace — checked at save time (`assertGraphRefsInWorkspace` in `automationGraph.ts`) and again at execution time (`assertListInWorkspace`/`assertFolderInWorkspace` in `automationTypes.ts`, since a list/folder can move/be deleted after the automation was saved). `targetWorkspaceId` (`move_list_to_workspace`, and the consolidated `list`/`folder` nodes' Move operation) is a deliberate exception — it names a *different* workspace by design, so it's instead checked against the automation **creator's own** workspace access (`assertGraphWorkspaceRefsAccessible`, `userCanAccessWorkspace`) at save time, and re-checked at execution time inside the action's `execute()`.
- **Permissions**: any workspace member can create their own automation; only the creator (or an admin) can rename/edit its graph/enable-disable/delete it/test it; every workspace member can view it and its run history read-only (`routes/automations.ts`).
- **Archiving**: `lists.is_archived`/`archived_at` is a genuine hidden state (not the workspace `is_public` flag, not trash), filtered out of `buildListsForUser`/`GET /api/lists` by default — set via the consolidated `list` node's **Edit** operation (`archived: true`/`false`, both directions) or the underlying `setListArchived()` helper directly. Surfaced via `GET /api/lists?archived=true` and a small **Archived** modal (`ArchivedModal.tsx`, opened from a Sidebar bottom-nav item next to Completed/Trash) — view + `PUT /api/lists/:listId/unarchive`, no expiry.
- **Testing**: each node in the editor (trigger and every action) has a small play-icon **Test** button. Clicking it calls `POST /api/automations/:id/test` (creator or admin only; disabled in the UI until the automation has been saved at least once), which builds a truncated graph containing the trigger plus every action up to and including the clicked node, **auto-picks a real, most-recently-touched task/list** in scope (no picker — e.g. the newest task in the trigger's scoped list for `task_completed`/`task_created`, or 400s with a clear message if nothing matches), and runs it for real through `runAutomation(..., {isTest: true})` — a genuine write, logged to `automation_runs` with `is_test: true` and surfaced with a purple "Test" badge in Run History. This is not a dry-run/simulation: it exercises the exact same execution path a live trigger would. Its response (`AutomationRunResult.steps[].output`) is also what feeds the editor's Data panel — see below.
- **Sync**: `automation` is a SIGNAL sync entity (like `template`) — `AutomationsScreen.tsx` refetches on `entityRevisions.automation` bumps rather than being patched in place like tasks/lists/folders/timelines.
- Frontend: `AutomationsScreen.tsx` (a per-item gallery, filtered by the `?ownerType=&ownerId=` it's opened with — see the owner-entity bullet above; no unfiltered/workspace-wide view) and `AutomationEditorScreen.tsx` (the flow-chart editor) at `/automations` and `/automations/:id`. Desktop uses `@xyflow/react` for a real drag/pan/zoom node canvas (edges are engine-managed, not user-drawn — adding/removing/reordering nodes always keeps the linear-chain invariant); mobile renders the identical graph as a vertical step-card list (`useMobile()` at the screen root, per the Mobile Responsiveness rules below) — both write the same JSON via `PUT /api/automations/:id`. `ParamsForm`/`ParamField` render `isListId`/`isFolderId`/`isWorkspaceId`/`isSectionId` params as dropdowns (the last populated from whichever sibling param `sectionListParam` names, default `targetListId`), `type: 'boolean'` params as a two-button toggle (`trueLabel`/`falseLabel`, default Yes/No), `isKeyValue` params (the HTTP action's headers/query params) as a repeatable key/value row editor, and `isLongText`/`isCode` params as a textarea (the latter styled as code, exempt from the drag-drop `{{...}}` token insertion described below in favor of a plain `input.<path>` JS accessor). `ParamsForm` filters out any field whose `showIf` condition isn't met by the node's current params before rendering it.
- **Data panel + drag-and-drop field picker**: a collapsible **Data** section under each node's params (both the desktop inspector and the mobile step-card) shows two `JsonTree` trees (`components/JsonTree.tsx` — a from-scratch recursive expandable JSON viewer, no library) sourced from the most recent Test result held in screen state (`testResult`; a deliberate V1 scope trim — it does not reach into older Run History entries): **Input** (`trigger`/`$json`/`nodes` — everything available to this node) and **Output** (this node's own result). Every field row in the tree is `draggable` (native HTML5 DnD, `text/plain` payload — the same convention already used by `CalendarScreen.tsx`'s chip drag, no DnD library); dropping one onto any text-producing param field (tracked cursor position via `onSelect`/`onClick`/`onKeyUp`) inserts a `{{...}}` expression token, or — for the Code action's textarea specifically, via a second custom-MIME payload the same drag also carries — a plain `input.<path>` JS accessor instead.

### AI Assistant

- Thin proxy to OpenRouter (`/api/ai/chat`). Requires `OPENROUTER_API_KEY`.
- **Sessions:** conversations live in `ai_chat_sessions` (30-day TTL); messages in `ai_chats` (role, content, `tool_calls`, `metadata`, `session_id`). Endpoints: `POST/GET /api/ai/sessions`, `GET/DELETE /api/ai/sessions/:id`, `POST/DELETE /api/ai/history`.
- **File context:** users can upload files into a chat (`POST /api/ai/files`); stored in `ai_chat_files` with extracted `content_text` (PDF via `pdf-parse`, spreadsheets via `xlsx`) and a 30-day TTL. A startup + 6-hour cron purges expired files.
- **Usage tracking:** every OpenRouter call records token counts in `ai_usage`.
- AI settings (`ai_assistant_enabled`, `ai_model`) live in `app_settings` and are admin-configurable from the Settings screen.

### Shared AI Tool Registry (single source of truth)

- **`backend/src/aiTools.ts`** is the one place AI capabilities are defined: each tool has a JSON-Schema parameter spec **and** a server-side SQL handler. `executeAiTool(userId, name, args)` runs a tool; `getOpenRouterToolDefs()` / `getMcpToolDefs()` adapt the same defs to each consumer.
- **Security invariant:** handlers receive `userId` from the verified credential only — there is **no `user_id` tool parameter**, and every query is scoped by `user_id`. This removes any prompt-injection path to another user's data. New tools must follow this rule.
- **`AiTool.mcpOnly`**: a tool flagged `mcpOnly: true` is excluded from `getOpenRouterToolDefs()` — the list both Sol and the Agent Runtime's own tool-calling loop draw from — while still included in `getMcpToolDefs()` for external MCP clients. Used exclusively by the 6 Agent Runtime meta-tools (`start_agent_run`, `get_agent_run`, `list_agent_runs`, `list_agent_proposals`, `accept_agent_proposal`, `reject_agent_proposal`) so an agent run can never call these on itself — an unbounded self-fork risk closed architecturally rather than with a runtime depth counter. See `DEPRECATIONS.md`.
- The registry now also carries **6 Graph Layer tools** (search/read/link/backlink entities), **2 Knowledge Layer tools** (hybrid search, get-status), the **6 `mcpOnly` Agent Runtime meta-tools** above, **7 Knowledge Base tools** (`create_knowledge_base`, `lookup_knowledge`, `list_knowledge_terms`, `create`/`update`/`delete_knowledge_entry`, `link_knowledge_entry`), and **9 AI Skills tools** (`list_skills`, `read_skill`, `list_skill_files`, `read_skill_file`, `create_skill`, `update_skill`, `delete_skill`, `set_skill_file`, `remove_skill_file` — see "AI Skills" below) — 30 new tools total, all following the same `userId`-scoped security invariant. The Knowledge Base tools add one restatement of that invariant: reads need workspace ACCESS, writes need workspace MEMBERSHIP — the same asymmetry `routes/knowledgeBase.ts` enforces, repeated in `aiTools.ts` because tools are a second entry point into the same data and must never be the looser one. The AI Skills tools add a DIFFERENT restatement, since skills are instance-wide rather than workspace-scoped: reads are open to any signed-in user (an enabled skill is exactly the context every user's assistant should already be drawing on) but scoped to ENABLED skills unless the caller is an admin, while every write (create/update/delete/file edits) re-derives admin status from `users.is_admin` inside the handler itself — see "AI Skills" below for why that check can't live in middleware the way `requireAdmin` does for the REST routes.
- **The Knowledge Base tools must stay self-sufficient for a caller with no UI.** An MCP client has no sidebar, so every step of the loop has to be reachable by tool call alone: `create_knowledge_base` makes the base (idempotent — it returns the existing one rather than erroring, mirroring `createBase()`); `list_knowledge_terms`/`lookup_knowledge` both carry the `entry_id` that `update`/`delete`/`link_knowledge_entry` require, since nothing else produces one; and `update_knowledge_entry` takes a `body` that replaces the definition text through `knowledgeBase/blocks.ts`'s `mutateEntryBlocks`, so an AI edit runs the same inline-link/mention/image-prune/embedding pipeline a human edit does. When adding a Knowledge Base tool, check the whole loop still closes without a human in it — a tool that reports "add one from the sidebar first" is a dead end to the caller that most needs it.
- **Internal AI** (`Sol`) fetches these defs from `GET /api/ai/tools` and executes data tools via `POST /api/ai/execute`; the frontend keeps only client-coupled tools (navigation, GPS browser-downloads, reorder/move, sublists, workspaces) — see `SUPERSEDED_CLIENT_TOOLS` in `components/AIAssistant/index.tsx`.
- File→text extraction is centralized in **`backend/src/fileText.ts`** (used by both `/api/ai/files` and the `read_file` tool).

### AI Skills

Admin-curated, **instance-wide** context bundles (Settings → AI Skills, a dedicated tab distinct from the AI tab's model/enable settings) that make Sol — and, by extension, the Agent Runtime and MCP clients, which all execute through the same tool registry — smarter and more personalized to this instance, without touching a system prompt or redeploying. An admin uploads a `SKILL.md` file (optionally with YAML-ish frontmatter, `---\nname: ...\ndescription: ...\n---`) or a `.zip` bundle containing one, can activate/deactivate each skill, and can also ask Sol to create/edit/delete skills entirely by chatting — "completely programmable, no UI required" is a deliberate design goal here, the same one the Knowledge Base tools hold themselves to.

- **Not workspace-scoped, unlike almost everything else in this app.** A skill affects every user's assistant instance-wide, which is *why* writes are admin-only rather than member-writable like the Knowledge Base — there is no natural "owner" to defer to the way a workspace has one.
- **`backend/src/aiSkills/skills.ts`** is the QueryExec-injectable data layer (`listSkills`/`getSkill`/`findSkill` (by id OR slug — the shape an AI tool call receives) /`createSkill`/`updateSkill`/`deleteSkill`/`listSkillFiles`/`getSkillFile`/`setSkillFile`/`removeSkillFile`), following the same convention as `knowledgeBase/entries.ts`: every mutator returns a discriminated `{ok, ...}` result rather than throwing. It also owns **`isUserAdmin(userId, exec)`** — the one new thing this feature introduces to the tool registry's conventions (see below) — and slug generation (`name` → lowercase-dashed, disambiguated with a numeric suffix on collision, never erroring).
- **`backend/src/aiSkills/bundle.ts`**'s `parseSkillBundle()` is a **pure function** (no DB) that turns a `.zip` buffer into `{skillMd, files, skippedCount}`: it locates `SKILL.md` case-insensitively at the archive root or one folder deep (the common "zip a folder" shape), captures every other file **relative to SKILL.md's own directory** (so a wrapping folder never leaks into stored paths, and a sibling file outside that folder is ignored), and enforces size/count caps **before** reading any entry content — total uncompressed size (10MB), entry count (300), and per-file size (256KB) — using the zip's central-directory metadata, the same "read the declared size before you extract" discipline a zip-bomb guard needs. Path safety (`isSafeZipPath`) rejects any entry that would escape the archive root once normalized, closing zip-slip **before** any path is ever joined with a filesystem or DB write. Only a small text-extension allow-list (`.md .markdown .txt .json .yaml .yml .csv .tsv .xml .html .htm`) is captured as a reference file; anything else (images, binaries) is silently skipped and reported back as a count, never stored — see the "reference files only" bullet below for why.
- **Reference files only — nothing here is EVER executed.** A skill's bundled files are plain text carried into the model's context, exactly like `SKILL.md` itself; there is no interpreter, no `eval`, no code-execution path attached to this feature at all. This is a deliberate scope boundary, not an oversight: the app's one narrow code-execution surface is the Automation Hub's `isolated-vm` sandbox (see "Automation Hub" above), built for a specific bounded purpose, and AI Skills does not extend that surface.
- **`routes/aiSkills.ts`** (`/api/admin/ai-skills`, `authenticate + requireAdmin` on every route — plain CRUD, no dedicated rate-limit tier): `GET /` (list all, enabled or not), `GET /:id` (one skill + its files' full content), `POST /` (create from pasted text), `POST /upload` / `PUT /:id/upload` (multer `memoryStorage`, 10MB cap — create/replace from an uploaded `SKILL.md` or `.zip`; a minimal hand-rolled frontmatter reader in the route file extracts `name`/`description` when present, falling back to the filename), `PUT /:id` (metadata/content/enabled), `DELETE /:id`, and `PUT`/`DELETE /:id/files` (admin per-file management, parity with the AI tools below). A `.zip` upload's content+files are written inside one `withTransaction` so a partial bundle can never persist.
- **`GET /api/ai/skills`** (`routes/ai.ts`, any signed-in user) is the lightweight, separate read surface: every **ENABLED** skill's `id`/`name`/`description` only, never the body — this is what feeds progressive disclosure (below), and is deliberately NOT the same endpoint as the admin list (which needs full content + disabled skills, admin-only).
- **Progressive disclosure into Sol's system prompt** (frontend): `useAiSkillsStore.ts` loads the enabled index once per session (`loadEnabled()`, called from `App.tsx` on login exactly like `useInstalledAppsStore`) and separately holds the full admin-management list (loaded on demand when the Settings tab opens). `buildSystemPrompt()` (`useAIStore.ts`) takes a `skills: SkillHint[]` param and appends every enabled skill's name+description as a short, cheap `skillsNote` — mirroring the exact pattern the Knowledge Base's `glossaryNote` already established — instructing the model to call **`read_skill`** for the full body **only once a task actually matches one**, rather than inlining every skill's full content into every single chat regardless of relevance. This is the same "index now, fetch on demand" split `lookup_knowledge` uses for the Knowledge Base glossary, and for the same reason: a growing library of skills must not linearly grow the token cost of every unrelated conversation.
- **9 AI tools** (`aiTools.ts`, none `mcpOnly` — available to Sol, the Agent Runtime, and MCP alike, per the registry's "one tool, three consumers" convention): `list_skills`/`read_skill`/`list_skill_files`/`read_skill_file` are READS, open to any signed-in user but scoped to **enabled** skills unless the caller is an admin (a disabled skill isn't "active" instance context yet, so a plain user calling `read_skill` on one gets `fail('this skill is currently disabled')`, not its content); `create_skill`/`update_skill`/`delete_skill`/`set_skill_file`/`remove_skill_file` are WRITES, admin-only. Because `AiTool.handler` only ever receives a `userId` (see the type's own comment above) — never a role — every write handler starts by calling `isUserAdmin(userId)` itself; there is no admin-gating middleware equivalent for tool calls the way `requireAdmin` gates the REST routes, so this is a **per-handler** check, the first of its kind in the registry. A non-admin's attempt fails cleanly with an "admin access required" `ToolResult` — it does not throw, and the tool remains listed for everyone (unlike `mcpOnly`, which hides a tool from a whole consumer class at the definition level, admin-gating here is a runtime decision made per call, since "is this caller an admin" isn't knowable at tool-registration time).
- **The Agent Runtime and MCP get these for free, by construction** — same registry, same `getOpenRouterToolDefs()`/`getMcpToolDefs()` adapters as every other tool, zero extra wiring in `agent/runtime.ts` or `mcpServer.ts`. A non-admin's workspace agent run that attempts `create_skill` simply gets the same admin-gated failure a non-admin chatting with Sol would.
- **The frontend AI Assistant refreshes the enabled index after a skill mutation mid-conversation** (`components/AIAssistant/index.tsx`'s `SKILL_MUTATION_TOOL_NAMES` check, alongside the existing backend-tool-triggered `appStore.loadFromApi()` refresh) so a skill created/edited/disabled by asking Sol is reflected immediately — both for the rest of that chat's own system-prompt-building on the next turn, and for the Settings → AI Skills tab if an admin has it open in another tab.
- **Admin UI** (`SettingsScreen.tsx`'s `ai_skills` tab + `modals/AiSkillUploadModal.tsx` / `modals/AiSkillEditModal.tsx`, both `createPortal`ed per the Mobile Responsiveness rules since they're opened from a routed screen): a card list of skills (name, description, enabled toggle, file count, an "SOL" provenance badge when `origin === 'ai'`) opening an edit modal on click — name/description/content are directly editable (buffered, explicit Save), bundled files are listed read-only with an expand-to-preview affordance, and a whole bundle can be replaced by re-uploading a new `SKILL.md`/`.zip` without recreating the skill. The upload modal offers two explicit modes (a two-button toggle, matching the app's established privacy-toggle pattern) — "Upload File" (drag/pick a `.md` or `.zip`, with optional name/description overrides) or "Write Manually" (paste content directly) — so an admin never needs a text editor and a separate upload step just to try a one-off skill.
- **Known V1 scope, deliberate:** skills are instance-wide only (no per-workspace skills — every skill informs every user's assistant equally); bundled reference files are text-only with no execution path whatsoever; there is no realtime SSE push when an admin toggles a skill for other already-open sessions (the enabled index is loaded once per login, matching `useInstalledAppsStore`'s own precedent, so a change is picked up on next sign-in/reload rather than live).

### Inline AI Assist (Notes & Markdown pages)

- A small **"Ask AI"** button lives inside `NotesEditor.tsx`'s header (rendered only when the caller passes an `aiContext` prop) — surfaced today in `TaskDialog.tsx`'s task notes and `TimelineScreen.tsx`'s milestone notes. It's a lightweight, single-turn assistant: clicking it opens a popover with quick-action chips (Summarize/Improve writing/Expand/Make concise, or Draft a note/Brainstorm ideas/Suggest next steps when the note is still empty) plus a free-text instruction box. It calls the existing `POST /api/ai/chat` directly (no dedicated backend endpoint) with a system prompt built from the full item context (`NoteAIContext` — title plus whatever `fields` the caller supplies, e.g. deadline/priority/status) and the current note text, then replaces the buffered note with the model's reply. An **"Undo AI edit"** button appears afterward to restore the prior text without having to Cancel the whole dialog.
- **Markdown pages get FULL programmatic control (create/read/edit/structure/delete), not just text generation.** The shared AI tool registry (`aiTools.ts`, exposed identically to the MCP server and internal Sol) carries a complete Markdown toolset: page-level **`list_markdown_lists`** / **`create_markdown_list`** (optionally seeded with initial blocks) / **`update_markdown_list`** (name/emoji/color/subtitle/visibility/full-width/folder — owner-only page settings) / **`delete_markdown_list`** (soft-delete to Trash, its auto-managed Todo list cascading with it), plus block-level **`get_markdown_list`** (every block with its id and type) and the mutators **`add_markdown_block`** / **`add_markdown_blocks`** (bulk insert) / **`update_markdown_block`** / **`remove_markdown_block`** / **`move_markdown_block`** / **`reorder_markdown_blocks`** (reorder the whole page by an exact id permutation) / **`set_markdown_content`** (wholesale restructure — replace the entire block list in one call). Block types match the page's own `/` slash commands: heading, paragraph, bulleted-list-item, numbered-list-item, todo, quote, divider (with an optional 2-column `layout`), link, image (image blocks can be reordered/re-captioned/preserved but never *created* by AI, since that requires a real file upload), and table (a `columns`/`rows` grid — `rows[0]` is the bold header row; each column carries a `width` and optional footer `aggregate` (`sum｜avg｜median｜max｜min`) over that column's numeric body cells, each row a `height`; the editor adds individually resizable columns/rows, add/remove row & column controls, and a per-column aggregate picker — rendered by the shared `frontend/src/components/MarkdownTable.tsx` (pure math in `utils/markdownTable.ts`), reused read-only on public share pages). One shared **`buildMarkdownBlockFromSpec()`** validates + constructs every block for all four entry points; `set_markdown_content` alone may keep an existing image (by referencing its `image_id`) and preserve a todo's live checkbox mirror (by carrying its original block `id`). All block mutators funnel through **`mutateMarkdownListBlocks()`** (`routes/markdownLists.ts`) — the same lock → reconcile-todos → prune-images → persist sequence the manual-edit `PUT` route's content branch uses, so a `/todo` block the AI adds mirrors into the auto-managed Todo list exactly like one typed by hand. `create_markdown_list`/`delete_markdown_list` reuse the exported **`createMarkdownListForUser()`** / **`deleteMarkdownListForUser()`** helpers that back the `POST` / `DELETE` routes, so an AI-created or AI-deleted page is byte-for-byte the same as a UI one.
- **Sol is markdown-page-aware, not just tool-equipped.** Having the 12 tools above in Sol's tool list isn't enough on its own — `buildContext()` (`useAIStore.ts`) has an explicit `pathname.startsWith('/markdown-list/')` branch (mirroring the existing `/list/`/`/timeline/`/`/gps`/`/calendar`/`/graph` branches) that inlines the currently-open page's own metadata and every block (via `markdownBlockSummary()`, a compact per-type projection: heading keeps `level`, todo keeps `checked`, table collapses to `header_row`/`body_rows`/`aggregates`, image never inlines its binary — just `image_id`/`caption`) as `Current context data`, and `buildSystemPrompt()`'s `viewDescriptions`/Guidelines both name Markdown Pages explicitly (a dedicated "MARKDOWN PAGES:" bullet alongside TEMPLATES/TIMELINES/etc.) — mirroring how every other major feature area gets both a data branch and a guideline callout, which is what actually makes Sol reach for `get_markdown_list`/`create_markdown_list`/etc. unprompted rather than needing the user to ask twice. The page lookup is `useMarkdownListsStore.getState().markdownLists.find(…)` — populated by the workspace-scoped `load()` `App.tsx` already calls on mount/switch (same store `MarkdownListScreen.tsx`'s own editor reads elsewhere), so no extra fetch is needed just to build context.
- **`MarkdownListAIAssist.tsx`** (`components/AIAssistant/`) is the "Ask AI" button + popover in `MarkdownListScreen.tsx`'s header — a full editor scoped to ONE page. Unlike Sol, it only ever sends the model this page's Markdown tools (`get_markdown_list`, `update_markdown_list`, `add_markdown_block`, `add_markdown_blocks`, `update_markdown_block`, `remove_markdown_block`, `move_markdown_block`, `reorder_markdown_blocks`, `set_markdown_content` — the cross-page `list`/`create`/`delete` tools are deliberately withheld), filtered from `GET /api/ai/tools` by name, and runs its own short tool-calling loop against `POST /api/ai/execute`, capped at 15 rounds. **Scoping is enforced client-side, not just by convention:** every tool call's `markdown_list_id` argument is force-overwritten with the currently-open document's id before execution, so the assistant can never touch a different page even if it hallucinates one. After any round that mutated the doc, the panel re-fetches it (`useMarkdownListsStore.getDetail`) and passes the whole page back to `MarkdownListScreen` (`onUpdated(md)`), so both its blocks/Todo mirror AND its own settings (name/emoji/…, e.g. after `update_markdown_list`) appear live without a manual reload.
- Both surfaces hide entirely whenever Sol itself would (AI Assistant disabled via `ai_assistant_enabled`, or `OPENROUTER_API_KEY` unset) — they read the same `/api/ai/settings` flag through `useAIStore`.

### CalDAV Server (external calendar apps)

- **`/caldav`** (mounted in `index.ts`, handler in `routes/caldav.ts`) is a read/write CalDAV server (a focused subset of RFC 4791 / WebDAV: `OPTIONS`, `PROPFIND`, `REPORT` `calendar-query`/`calendar-multiget`/`sync-collection`, `GET`, `PUT`, `DELETE`, `PROPPATCH`). It lets Apple Calendar, Thunderbird, etc. subscribe to everything on the Calendar page. Mounted outside `/api` (no rate limiter) and proxied by Nginx (`/caldav` + `/.well-known/caldav`).
- **Auth: HTTP Basic** with the user's email + a generated CalDAV app password (`caldav_credentials`, bcrypt hash only, one per user, revocable) — never the account password. Helpers in `caldav/credentials.ts`.
- **Collections:** one calendar per accessible workspace (`ws-<id>`) exposing milestones as **VEVENT** and tasks as **VTODO** (both read-only), plus a writable **`meetings`** calendar (standalone meetings as VEVENT; inbound `PUT`/`DELETE` upsert/remove rows, and `meetings.caldav_uid` maps a client-chosen resource name back to its row). Data scope mirrors the in-app Calendar page (all accessible workspaces).
- iCalendar (de)serialization is hand-rolled in **`caldav/ical.ts`** (floating local times, stable per-item `DTSTAMP`/`ETag`); the data layer is **`caldav/data.ts`**. Connection management (status / (re)generate password / revoke) is `routes/caldavManage.ts` → `/api/caldav`, surfaced in the **Calendar Sync** tab of `UserSettingsModal`.

### MCP Server (external AI agents)

- **`/mcp`** (mounted in `index.ts`, handler in `routes/mcp.ts`) is a Model Context Protocol server over **Streamable HTTP** (`@modelcontextprotocol/sdk`, stateless: one server+transport per request). It exposes the shared registry to external agents (e.g. the Claude MCP connector). Nginx proxies `/mcp` with buffering off. `backend/src/mcpServer.ts` wires the server's capabilities (tools + resources + prompts).
- **Resources (`backend/src/mcpResources.ts`)**: a `solytiq://` URI scheme exposing 2 static resources (e.g. instance-wide catalog info) plus 5 URI templates (e.g. `solytiq://entity/{type}/{id}`, and `solytiq://knowledge/{workspaceId}/glossary` + `/term/{term}` which let a client pull a workspace's vocabulary as CONTEXT instead of tool-calling per term — a term with no definition returns a read *result* rather than 404, since "no definition exists" is exactly what the caller needs to know and a 404 would be indistinguishable from a permission failure) that resolve a specific entity through the same `graph/visibility.ts` boundary as everything else. `resources/subscribe` is accepted per the MCP spec but is **permanently inert** — this is a stateless one-server-per-request transport with no live connection to push update notifications through, so a subscription has nowhere to deliver to; documented rather than silently ignored.
- **Prompts (`backend/src/mcpPrompts.ts`)**: 4 prompt templates an MCP client can surface as slash-command-style shortcuts (e.g. "summarize this workspace," "find related items").
- **Tools**: the full shared registry from `aiTools.ts` via `getMcpToolDefs()`, including the 14 Graph/Knowledge/Agent-Runtime tools described in Shared AI Tool Registry — the only consumer that sees the 6 `mcpOnly` Agent Runtime meta-tools, since `getOpenRouterToolDefs()` (Sol, the Agent Runtime's own loop) excludes them.
- **Auth: bearer tokens minted via OAuth.** Agents send `Authorization: Bearer solytiq_pat_…`. Tokens live in `api_tokens` (only a SHA-256 hash is stored), are long-lived and individually revocable. PAT helpers are in `backend/src/apiToken.ts`. A missing/invalid token returns `401` with a `WWW-Authenticate: Bearer … resource_metadata="…"` header pointing at the Protected Resource Metadata doc, which kicks off the OAuth handshake.
- **OAuth 2.1 connector flow** (`routes/oauth.ts`): the user connects Claude from the **Claude MCP** section of the per-user `UserSettingsModal` by pasting the `/mcp` URL into Claude as a custom connector. Claude then runs OAuth discovery → Dynamic Client Registration → authorization → token exchange:
  - **Discovery:** `GET /.well-known/oauth-protected-resource[/mcp]` (RFC 9728, resource→authorization-server pointer) and `GET /.well-known/oauth-authorization-server` (RFC 8414, endpoint metadata) — both served from `index.ts`, using `getPublicBaseUrl()` (`publicUrl.ts`, prefers `PUBLIC_URL`/`FRONTEND_URL`).
  - **DCR:** `POST /api/oauth/register` (RFC 7591) stores the client (`oauth_clients`: `client_id`, `client_name`, `redirect_uris`) and returns a public PKCE `client_id` (`token_endpoint_auth_method: none`).
  - **Authorize:** `GET /api/oauth/authorize` validates `response_type=code`, the client + `redirect_uri`, and that PKCE `code_challenge` (S256) is present, then redirects to the React `/oauth/consent` screen.
  - **Consent:** `POST /api/oauth/approve` (session-JWT authenticated) mints a single-use, 5-minute authorization code bound to `user_id` + `client_id` + `redirect_uri` + `code_challenge` (`oauth_codes`).
  - **Token:** `POST /api/oauth/token` (`grant_type=authorization_code`) consumes the code atomically, verifies the PKCE `code_verifier` (S256, constant-time), and returns a `api_tokens` PAT scoped to the consenting user — so the connector can only ever do what that user can do in-app.
- **Token management:** `GET`/`DELETE /api/tokens` (`routes/tokens.ts`) list and revoke (disconnect) connected clients; there is no manual token-creation endpoint — tokens are minted only by the OAuth flow.

### n8n Community Node (`n8n/`)

- **`n8n/`** at the repo root is the source of the published `n8n-nodes-solytiq-cloud` npm package — an n8n community node that wraps the instance-wide Admin API (`backend/src/routes/adminReadApi.ts`). It covers every resource the route exposes (Export, User, Workspace, Folder, List, Section, Item, Timeline, Milestone, Meeting) with dropdowns dynamically loaded from the instance, plus a polling trigger node. See `n8n/README.md` for its own architecture and release notes.

### Mobile Responsiveness

Every new component, screen, modal, dialog, and popup **must work correctly on mobile (≥ 390px, e.g. iPhone 15 Pro)**. Desktop layout is the design priority; mobile is an adaptive layer on top.

Rules:
- Call `useMobile()` (from `src/hooks/useBreakpoint.ts`) at the composition root (screen, modal, or layout shell). Never call it inside leaf/reusable components — pass `isMobile` as a prop if needed.
- Never set `transform` on a `position: fixed` container (e.g. the sidebar). CSS spec makes `transform` a new containing block for fixed descendants, trapping them inside and breaking overflow. Use `left`/`top` properties instead for slide animations on fixed elements.
- **Any modal rendered from inside a routed screen component (i.e. anything under `<Route>` in `App.tsx`) must render via `createPortal(..., document.body)`.** The per-route wrapper (`.page-transition` in `App.tsx`) plays the `pageIn` keyframe animation with `animation-fill-mode: both`, so it's left with a non-`none` `transform: translateY(0)` indefinitely after mounting — which makes it a containing block for `position: fixed` descendants. A modal that isn't portaled gets trapped inside that wrapper's bounds instead of covering the viewport, so its backdrop blurs the page content but not the `TopBar`/`Sidebar` next to it. Modals rendered at the `AppLayout` root (keyed off the top-level `modal` string, e.g. `AddWizard`) aren't affected since they sit outside `.page-transition` — only modals owned by a screen itself (see `TemplatesScreen.tsx`'s `CreateTemplateModal`/`UseTemplateModal`/delete-confirm for the reference pattern) need the portal.
- All fixed overlays (dropdowns, dialogs, rename modals) must use `position: fixed` with `zIndex` ≥ 400 so they escape any parent `overflow: hidden`.
- Pickers (`CalendarPicker`, `TimePicker`) use `Math.min(N, window.innerWidth - 32)` for their width to stay on-screen.
- Use `padding: 'var(--modal-pad)'` (defined in `index.css`) for modal backdrops so padding shrinks on mobile without JS.
- Test both 390px (mobile) and 1440px (desktop) after every change — desktop must remain unchanged.
- **`npm run test:responsive` enforces the no-horizontal-scroll rule** in a real browser at 320/375/390/639/640/768/1024/1440, on every route reachable without a backend, and names the offending element when it fails. It is deliberately not a screenshot diff: a pixel baseline goes stale on any intentional design change and reports "something moved", where this reports "the page scrolls sideways at 320px". Same no-backend scope as `test:a11y` — screens behind `<Protected>` are not covered, and that gap is stated rather than hidden.

### Home Screen Install (iOS "Add to Home Screen" + macOS Chrome/Safari)

The app is installable as a standalone window (no browser address bar/chrome) on iOS (Home Screen), and on macOS via Chrome/Edge/Chromium's native "Install [App]" prompt or Safari 17+ (macOS Sonoma+)'s "Add to Dock" — one plain web-standards PWA shell serving all of them, not a native app: no App Store/Mac App Store listing, no Apple Developer account, no service worker. Desktop support needed **no new manifest, icons, or meta tags** — Chrome/Edge/Chromium's installability check and Safari macOS's Dock support both read the exact same `manifest.webmanifest` already shipped for iOS.

- **`frontend/public/manifest.webmanifest`** is the Web App Manifest (`name`/`short_name`/`icons`/`start_url: "/"`/`scope: "/"`/`display: "standalone"`/`background_color`/`theme_color`). iOS Safari only started honoring the manifest's `display`/`icons`/colors itself in iOS 17.4 — `frontend/index.html`'s `apple-mobile-web-app-capable`/`apple-mobile-web-app-status-bar-style`/`apple-mobile-web-app-title` meta tags plus an `apple-touch-icon` link are what make standalone install behave correctly on older iOS too (these meta tags are iOS-specific and irrelevant to desktop Chrome/Safari, which install from the manifest alone). `start_url: "/"` is deliberate and needs no maintenance as routes change: the root route already resolves to the right place for any auth state (`resolveHomeRoute(lastRoute)` if logged in, `/setup` or `/login` otherwise — see `App.tsx`), so the installed icon always opens somewhere sensible.
- **Icons are a flattened, opaque square — never the raw logo file.** `frontend/public/solytiq-cloud.png` has a rounded-square silhouette baked in with transparent corners (it's designed to be dropped into an already-rounded UI avatar slot). iOS applies its **own** corner mask to whatever `apple-touch-icon` it's given and paints any transparent pixels solid **black** — passing the raw file straight through produces black corner triangles on the Home Screen. `frontend/public/icons/` (`apple-touch-icon.png` 180×180, `icon-192.png`, `icon-512.png`) are regenerated from it by flattening the transparent corners onto the brand primary (`#5e4dbb`) onto a full-bleed square, then letting iOS/Android/desktop Chrome apply their own rounding on top — the same `icon-192`/`icon-512` pair the manifest already declares is exactly what Chrome's install prompt and Safari's Dock icon use, no separate desktop asset needed. Regenerate with `sharp` (crop to a centered square, `.flatten({ background: '#5e4dbb' })`, resize) if the source logo ever changes — don't hand-edit the generated PNGs.
- **`apple-mobile-web-app-status-bar-style: black-translucent`** was chosen deliberately over `default`/`black`: it makes the standalone status bar overlay the content edge-to-edge, matching the exact safe-area behavior the app's mobile CSS already handles for regular full-screen Safari (`env(safe-area-inset-top)` in `TopBar.tsx`/`Sidebar.tsx`, gated on the existing `viewport-fit=cover` meta viewport) — no new safe-area work was needed because standalone mode reuses the same insets regular mobile Safari already accounts for. Irrelevant on macOS — a Dock/installed app window has no status bar to inset.
- **No service worker, on purpose — true on desktop too.** The ask this satisfies is "installable + launches standalone," not offline support. iOS's Add to Home Screen has never required a service worker; Chrome relaxed its own desktop installability criteria the same way, so `beforeinstallprompt`/the omnibox install icon fire off the manifest alone, no `fetch`-handling service worker required. Adding one later for offline caching would need real care around this app's auth model (JWT in `localStorage`) and the cursor-based SSE delta-sync engine (`useSyncStore`) so a stale cache can't serve outdated data or fight the sync cursor — don't bolt one on casually.
- **`nginx/nginx.conf`** serves `manifest.webmanifest` with an explicit `application/manifest+json` content type and a short (not long-cache-immutable) cache lifetime — unlike hashed JS/CSS bundles, the manifest's filename never changes across deploys, so it must stay cheaply revalidate-able.
- **Detection is platform-agnostic by construction.** `frontend/src/utils/homescreen.ts`'s `isHomeScreenApp()` checks `window.matchMedia('(display-mode: standalone)')` first, which the spec defines to match an installed PWA window on *any* platform — a macOS Chrome/Edge install or a Safari "Add to Dock" window reports `standalone` exactly like an iOS Home Screen launch, so no platform branch was needed there. `navigator.standalone` is kept only as an iOS-specific fallback.
- **Device labeling IS platform-specific**, since desktop browsers deliberately freeze/omit the precise OS build in their UA string for privacy (Chrome's User-Agent Reduction, Safari's long-standing `10_15_7` placeholder) — an exact macOS version isn't reliably recoverable client-side, unlike iOS's `OS 17_4_1`-style UA token. `detectHomeScreenDevice()` branches on the UA: iPhone/iPad/iPod get a device name + parsed `iOS X.Y.Z`; a Mac gets `Mac (<Browser>)` (Safari/Chrome/Edge/Firefox/Opera, sniffed in that FIRST-match-wins order since Edge/Opera/Chrome UAs all also contain the substring `Safari/...`) with `osVersion` fixed to the literal string `'macOS'` rather than a fabricated version number. Unit-tested against real UA strings for each browser in `homescreen.test.ts` (no DB, no backend involved — pure UA parsing).
- **Usage is tracked, not just installability.** Account Settings → Mobile → **Home Screen App** lists every device that has opened the app in standalone mode — iOS and macOS alike (`homescreen_connections` — see "Authentication" above), alongside the native mobile app's own device list, so a user can see at a glance which of their devices actually use the installed icon. The backend endpoint (`POST /api/auth/homescreen-connections/ping`, `routes/auth.ts`) stores whatever `deviceName`/`osVersion` strings the client sends with no platform-specific validation, so it needed zero changes to support Mac entries.

### Styling — "Luminous List" Design System

- Tailwind CSS v4 provides base styles (`src/index.css`), but components predominantly use **inline `style={{}}` objects** with the design tokens below. Match the surrounding component's approach when editing.
- Aesthetic: glassmorphism, soft purples, rounded cards, springy modal animations.
- **Palette:** primary `#5e4dbb`; light purple surfaces `#F5F3FF`/`#f0edff`; text `#1c1b22` (primary) / `#484552` (secondary) / `#73707f` (tertiary) / `#b0acbe` (quaternary); borders `#e8e4f0`/`#E5E7EB`; dividers `#f0ecf8`; success `#10B981`; error `#ba1a1a`; warning `#d97706`.
  - **`--color-text-tertiary` is the AA floor.** It was `#787584` — 4.491:1 on white, missing WCAG AA's 4.5:1 by 0.009, and 4.213:1 on the app's own tinted surfaces. As the workhorse secondary-text colour that failed on nearly every screen at once; `#73707f` is the smallest darkening that clears 4.5:1 against both.
  - **`--color-text-quaternary` is de-emphasis only** (placeholders, disabled hints, decorative captions) and is 2.07:1 on white by design. Never use it for text that carries information — `npm run test:a11y` fails the build when it appears on real content.
- **Type:** Hanken Grotesk for headings/labels/UI, Inter for body.
- **Radii:** buttons 8–10, cards/modals 14–20, pills 9999. **Shadows:** subtle purple-tinted (`0 8px 32px rgba(0,0,0,0.14)`, `0 8px 40px rgba(94,77,187,0.10)`).
- **Animations live in the central Animate-UI layer, never in CSS.** `src/components/animate-ui/` is the ONE place permitted to import `motion/react` (values *and* types), and `npm run check:animations` fails the build on any `@keyframes`, CSS `animation`/`transition` declaration, `requestAnimationFrame`, injected `<style>` block, or raw `motion.*` import outside it. Its allowlist is empty by design — an exception is a reviewed entry, never a silent one.
  - **Never put a raw `transform:` string in a Motion animation target** (`animate`/`initial`/`exit`/`while*`) — write `scale: 1.08`, `x: 4`, `rotate: 90` instead. Motion composes `transform` from its own keys and has no value type for the shorthand, so it mixes the string against the element's computed origin (`none`), which shares no numeric format with `scale(1.08)`; the tween resolves to garbage and settles on `scale(0)`, silently shrinking the element to nothing on hover. `check:animations`' `motion-transform-string` rule gates this. A static `style={{ transform: 'translateY(-50%)' }}` is fine — Motion never reads it.
  - Reach for a shared primitive first: `MotionIn` (`motion.div`), `MotionButton` (`motion.button`, keeps native button semantics), `MotionDraggable` (native HTML5 drag rows — see below), `ModalIn`/`PopIn`/`PageIn`, `Spinner`. Shared curves, durations and variant sets are in `motionTokens.ts` (`EASE_SPRING`/`EASE_SETTLE`/`EASE_STANDARD`/`EASE_OUT_CUBIC`, `modalVariants`, `listItemVariants`, …).
  - **`MotionDraggable` is required for any row using native HTML5 drag** (`draggable` + `onDragStart`/`onDragOver`/`onDrop`). Motion's types claim those prop names for its own pan gestures; `MotionDraggable` re-types them and never passes Motion's `drag` prop, so the native handlers keep reaching the DOM. `motionDraggable.test.tsx` locks that behaviour in — if a Motion upgrade ever makes the types honest, it goes red instead of drag-and-drop silently breaking.
  - **`useFrameLoop` is the only sanctioned per-frame callback**, and `nextFrame` the only one-shot frame deferral (a caret restore after React commits). Both run inside Motion's own frame scheduler rather than starting a rival `requestAnimationFrame` that would interleave its DOM writes with Motion's reads. `useFrameLoop`'s `reducedMotion` option distinguishes `'stop'` (decoration — do not run) from `'settle'` (motion that also COMPUTES the layout, e.g. the force simulation — run, reach a resting state, then stop).
  - **Reduced motion**: `MotionConfig reducedMotion="user"` at the app root covers transform/layout animations. It does NOT cover a decorative repeat you opted into yourself (a keyframe array with `repeat: Infinity`, `backgroundPosition`, …) — gate those on `useReducedMotion()` explicitly. `index.css` keeps one global `prefers-reduced-motion` fallback purely as defence in depth for third-party CSS (Leaflet, XYFlow, sigma); the checker exempts declarations inside such a block, since suppressing motion is not motion.
- **Icons:** Material Symbols via the `<Icon>` component (`src/components/Icon.tsx`) — pass the symbol name as a string.
- **Privacy/visibility toggles:** two-button (lock/public) pattern; selected gets `#5e4dbb` border + `#f0edff` background + a check icon.
- **Date pickers:** Always use the shared `<CalendarPicker>` component (`src/components/CalendarPicker.tsx`) for *every* calendar/date field — never a native `<input type="date">` (it renders the OS picker, which breaks the design language and is locale-dependent). The established pattern is a trigger button (`calendar_today` icon + the formatted date or a placeholder + an `×` clear affordance) that toggles a `showExpiryCal`-style boolean, with `<CalendarPicker value={…} onChange={…} onClear={…} />` in an absolutely-positioned popover. See the expiry fields in `FilesScreen` and `ItemSettingsModal`, and the due-date field in `TaskDialog`, for reference.
- **Time pickers:** Likewise, always use the shared `<TimePicker>` component (`src/components/TimePicker.tsx`) for *every* time-of-day field — never a native `<input type="time">` (same OS-picker problem). It takes/returns a 24-hour `"HH:MM"` string and mirrors `CalendarPicker`'s chrome (same card, hour/minute scroll wheels with the selected value highlighted in `#5e4dbb`, and a **Now** / **Clear** footer). Wire it with the identical trigger-button + `showTime`-boolean + absolutely-positioned popover pattern as the date picker (a `schedule` icon + the `HH:MM` value or a `--:--`/placeholder). See the **Time** field in the `TimelineScreen` milestone editor and in `AddTimelineWizard` for reference.

### Task Source Duality

Tasks belong to one of two sources:
- `'dash'` — created from the Dashboard, not inside a list
- `'list'` — created inside a specific list/section

This affects which store actions to call: use `updateDashTask` for dash tasks and `updateListTask`/`deleteListTask` for list tasks. Always check `task._source` before dispatching.

### Sublists & Linked Lists

A list task can link to another list via `linkedListId` + `linkedListType`:
- `'sublist'` — a child list owned by this task (`lists.parent_task_id` + `depth`); progress rolls up into the parent's `linkedProgress` ring.
- `'link'` — a reference to an existing standalone list.

Create them via `apiCreateSublistTask` / `apiLinkListAsTask`. Sublists always share the parent's `workspace_id`.

### Board / Markdown Page UI naming vs. the `list` / `markdownList` entities

The `ListScreen`/`AddListWizard` feature is labeled **"Board"** in user-facing text (nav, wizards, dialogs, empty states), and the `markdownList` feature is labeled **"Markdown Page"** — these are display-label renames only. The underlying `List`/`MarkdownList` types, `lists`/`markdown_lists` DB tables, `/api/lists/*` and `/api/markdown-lists/*` routes, `list_id`/`listId`/`markdown_list_id` fields, `ListScreen.tsx`/`MarkdownListScreen.tsx` filenames, and store actions (`useAppStore.lists`, `updateListTask`, `useMarkdownListsStore`, etc.) all keep their original names. When adding new user-facing text, say "Board" / "Markdown Page"; when touching code, keep using `list`/`List` and `markdownList`/`MarkdownList`.

### Board Screen: List vs Kanban vs Timeline View

`ListScreen.tsx` renders a **List/Kanban/Timeline tab switcher** at the top-left of the page (above the progress hero). List and Kanban render the exact same data via the same handlers (drag state, `handleDrop`/`handleDropOnSection`/`handleSectionDrop`, `handleAddTask`, section CRUD) — only the layout differs:
- **List** (default): sections stacked vertically, each a full-width block — the original layout.
- **Kanban**: sections rendered as horizontal columns (`lists.sections` → columns), each task a card (the same `TaskItem`). Dragging a card onto another column moves the task there (`sectionId` update + reorder); dragging a column's drag-handle reorders columns left-to-right using the same section-reorder endpoint as the List view's top-to-bottom reorder.
- **Timeline** (`frontend/src/components/TaskTimelineView.tsx`): a horizontally-scrollable, left-to-right Gantt-style view — rows grouped by section (same order as List view), each task rendered as a bar from its creation date to either its completion date (checked) or "today" (still open, so the bar grows day by day until it's checked). A task's `deadline`, if set, renders as a separate flag marker on the row — colored red when the task is still open and past its deadline. A dashed "today" line runs through the grid, with **Day / Week / Month** zoom controls and a **Today** button that re-centers the horizontal scroll. Clicking a task's row or bar opens the same `TaskDialog` as List/Kanban; the row checkbox calls the same `toggle` handler (including its auto-sort-to-bottom behavior) and renders the same checkmark glyph as List/Kanban once checked.
  - **Zoom stretches to fill the panel:** each zoom level's day/week/month pixel-per-day is a *minimum* (detail floor), not a fixed width — a `ResizeObserver` on the scroll container measures the visible chart width, and when the task date range would render narrower than that, `pxPerDay` is stretched up (`Math.max(basePxPerDay, containerWidth / totalDays)`) so the grid always fills the full width with no dead space. Longer ranges that don't fit still scroll normally at the zoom's base density.
  - **`tasks.completed_at`** (`TIMESTAMPTZ`, nullable) is a dedicated column set to `NOW()` the moment `checked` flips true and cleared to `NULL` when unchecked (`CASE WHEN $checked IS NULL THEN completed_at WHEN $checked THEN NOW() ELSE NULL END` in both `updateListTaskFields` and the dash-task `PUT /api/tasks/:id` handler) — deliberately independent of `updated_at`, which also moves on unrelated edits made after completion and would otherwise shift a completed task's bar end. Existing checked tasks are back-filled once from `updated_at` in `runMigrations()`. Exposed to the frontend as `Task.completedAt`, and to `created_at`/`completed_at`'s full time-of-day precision via each bar's hover tooltip (`hh:mm - dd.mm.yyyy`, local time).
  - **`TaskDialog`'s Timeline row**: the properties panel's last row (icon `history`) renders `TaskMiniTimeline` — a compact, read-only, auto-filled "Created → Done" strip (same `hh:mm - dd.mm.yyyy` format) with a connecting bar (solid once done, dashed while open) between the two points. Once checked, a duration badge ("time it took to finish", `HH:MM` — total hours, unbounded, not clock-wrapped — elapsed between `createdAt` and `completedAt`) appears at the end of the row. Reflects the task's persisted, saved state — not the dialog's buffered/unsaved edits.
- The active view is **persisted per list** in `lists.view_mode` (`'list' | 'kanban' | 'timeline'`, default `'list'`) — a plain column set via `PUT /api/lists/:listId` (`viewMode` in the body) and synced like any other list field, so switching view on one device shows the same view everywhere. It is **not** a separate entity — same list, same sections, same tasks, just a different `view_mode`. (This is unrelated to the standalone **Timeline** entity — `timelines`/`milestones`, `TimelineScreen.tsx` — which is a distinct top-level feature for dated milestone roadmaps.)
- **Keyboard shortcuts** `1`/`2`/`3` (registry ids `view-list`/`view-kanban`/`view-timeline`, see Keyboard Shortcuts below) switch the tab switcher directly, same as clicking a pill. Whichever view becomes active mounts with the `viewSwitchIn` keyframe (`index.css`) — a quick fade + upward settle — for a consistent, deliberate transition regardless of whether the switch was triggered by mouse or keyboard.

### Board Screen: Quick Add (staging tray + section prediction)

An opt-in, **per-board** input bar (Board settings → Appearance → **Quick Add**, `lists.quick_add_enabled`, off by default) rendered by `frontend/src/components/QuickAddBar.tsx` **directly beneath the board's header box**, above whichever of the three views is active — prediction is a property of the board, not of how it happens to be laid out right now.

- **Items land in a STAGING TRAY, not in a section.** A Quick Add item is created with `section_id = NULL` and rendered in a tray immediately below the bar. It is a real task — checkable, openable, draggable, and **counted in the board's progress totals** — it just hasn't been filed yet. Surfaced on the list payload as `List.stagedTasks` by `stagedTasksOf()` (`routes/lists.ts`), which all four list builders (`buildListsForUser`/`buildListsPageForUser`/`getListForUser`/`getListsForUserBatch`) feed from the `'__none__'` bucket they already computed and previously discarded. **This also un-hides a pre-existing class of orphan**: `tasks.section_id` has always been `ON DELETE SET NULL`, so deleting a section already orphaned its items into a state no screen rendered while still counting them in the totals — those rows now appear in the tray instead of looking like data loss.
- **The suggestion, twice.** While typing (debounced via `useAsyncData`'s `debounceMs`, `lexicalOnly: true` so no embedding-provider round trip fires per keystroke) a passive hint reads *"Looks like 🔨 Doing · Similar to 'Fix login bug'"*. After **Enter**, actionable **"Move to {SECTION}"** chips appear; clicking one animates the row out of the tray and into that section. **Tab** accepts the live hint outright — add and file in one gesture. The item is deliberately predicted BEFORE it is inserted, or it would be its own strongest evidence.
- **Dragging works both ways.** The tray is modelled as a pseudo-section (`STAGED = '__staged__'` in `ListScreen.tsx`) so the existing cross-section drop handlers move items in and out of it unchanged. Dragging an item OUT of a section into the tray needs `PUT /api/lists/:listId/tasks/:taskId` with `stage: true` — `sectionId: null` cannot express it, since every other field there treats null as "unchanged" (`COALESCE`), the same shape `updateLinkedList` already uses.

#### The memory: two tables, and why that IS the "last section only" rule

**`backend/src/quickAdd/`** — `titleKey.ts` (pure normalization), `ranking.ts` (pure scoring), `memory.ts` (recording), `predict.ts` (retrieval), `kbBubble.ts` (the Knowledge Base surface), `embedder.ts` (embedding sweep), `backfill.ts` (one-time seed).

| Table | Role |
|---|---|
| `section_placement_events` | **Append-only history.** Every create/move/stage/delete, with the section id AND a label snapshot so a row stays readable after the section is renamed or deleted. **Nothing in the prediction path reads this table.** |
| `section_memory` | **The projection the predictor reads.** PK `(list_id, title_key)`, holding exactly ONE row per remembered item title, whose `last_section_id` is by construction the most recent placement. |

That split is the whole design. *"Only the LAST section may drive a suggestion"* is enforced by the **primary key** — a new placement UPSERTs over the previous section rather than appending — **not** by a `WHERE`/`ORDER BY … LIMIT 1` a future query could forget. The earlier states are still stored, in the table the predictor has no reason to open, so a future "journey of this item" view costs nothing and still cannot leak into what the suggestion says.

- **`recordPlacement()` (memory.ts) is the only writer**, and `createListTask`/`updateListTaskFields`/`deleteTaskRow` in `routes/lists.ts` are the only call sites — the same choke points every section move in the app already funnels through (drag-and-drop, Kanban columns, `TaskDialog`, an accepted suggestion, an Automation Hub `move_task`), so no call site has to remember to teach the board anything. Best-effort and **never throws into the caller's save**, the same contract `mentions.ts`/`graph/inlineLinks.ts`/`knowledge/queue.ts` hold.
- **A delete or an un-file writes history but LEAVES the projection standing** — "where does an item called this belong" stays true after the specific task is gone, which is exactly the asked-for behaviour: the board remembers items it no longer holds.
- **`last_section_id` CASCADEs on section delete**: a memory naming a section that no longer exists could only ever produce a suggestion nobody can act on. The event history keeps the deleted section's label regardless.

#### Prediction (`predict.ts` + `ranking.ts`)

Four retrieval channels, fused by the Knowledge Layer's own **Reciprocal Rank Fusion** (`knowledge/fusion.ts`) — the channels' raw scores aren't on comparable scales, their rank positions are:

| Channel | Source | Needs |
|---|---|---|
| `exact` | the normalized title has been placed on this board before | nothing |
| `lexical` | pg_trgm `similarity()` over `title_key` | pg_trgm |
| `word` | pg_trgm `word_similarity()` — the query as a phrase inside a longer remembered title | pg_trgm |
| `vector` | pgvector cosine over `section_memory.embedding` | pgvector **+** an embedding key |

The first three need only pg_trgm, which this schema has always had; **the vector channel is strictly additive** and checks reality (`isPgvectorAvailable()`, is a key configured) rather than a flag, exactly like `knowledge/search.ts`. Matching runs on the NORMALIZED key, so it never depends on how a title was capitalized or punctuated. A JS word-overlap channel (`token`) is computed over the already-retrieved candidates rather than costing a fifth query.

Each surviving memory row votes for its ONE section, weighted by fused score × recency (45-day half-life, floored — old memory still beats none) × repetition (logarithmic, so one pathologically repeated item can't drown the board). Confidence is the winner's share of the vote, damped by an **evidence** factor that is channel-aware: an exact hit saturates on its own (one verbatim repeat is the strongest signal this feature has), a fuzzy one needs corroboration. Anything under `MIN_CONFIDENCE` is dropped rather than shown as a guess.

- **Every pure part is unit-tested with no DB** (`__tests__/quickAdd.test.ts`); **`quickAdd.integration.test.ts` covers what a mock `QueryExec` structurally cannot** — that the trigram channels actually retrieve, that the projection holds one row naming the last section after a real chain of moves, that a staged item round-trips into `stagedTasks`. It earned its keep immediately, catching two defects the mocked suite passed clean: an UPSERT naming `embedding` unconditionally (which fails on a plain `postgres:16` image, and, because recording is best-effort, would have left every board learning **nothing** while appearing to work), and a bubble sweep ordering by a `lists.updated_at` column that does not exist.

#### The Knowledge Base bubble

Every Quick Add board gets **one** `knowledge_entries` row (`lists.quick_add_kb_entry_id`) — its own bubble on the `/knowledge` net, opening in the normal `EntryInspector`, indexed into the Knowledge Layer, and reachable by Sol/MCP through the existing knowledge tools, none of which needed new code. `entry_type: 'system'`, `origin: 'extracted'` (the inspector badges it **"Scanned"** — machine-derived from the workspace's own activity; `'ai'` would falsely badge it as Sol-authored), linked to its board by a real `knowledgeEntry --[defines]--> list` edge so it renders beside the board rather than floating among the workspace's terms. `createBase()` is idempotent, so enabling Quick Add on a workspace with no Knowledge Base creates one — a user shouldn't need to know the Knowledge Base exists to flip a board setting.

**ONE entry per board, not one per remembered item** — a busy board would otherwise add hundreds of rows to a dictionary a human curates and Sol reads every turn. The placements live INSIDE the bubble, as a rendered table in its body.

**The bubble is a PROJECTION, never the source of a prediction.** Editing its table by hand changes what a person reads, not what the predictor decides — the predictor never opens it, and deleting the bubble entirely does not stop suggestions (`syncBubble` clears the pointer and respects the deletion rather than resurrecting it). That asymmetry is deliberate: a readable mirror can be reconciled; a dictionary entry anyone can retype is not something a ranking algorithm should trust. Regeneration is **debounced** — `recordPlacement` flags `lists.quick_add_memory_dirty` and `sweepDirtyBubbles()` reconciles it on an interval, the same dirty-flag-plus-interval shape `graph/metrics.ts` uses for pagerank, rather than rewriting a JSONB document per dragged card.

#### Endpoints, sweeps, backfill

- `POST /api/lists/:listId/quick-add/predict` (`{ title, lexicalOnly? }` → ranked suggestions; a failure returns `[]` rather than an error — a missing hint is a working Quick Add bar), `POST /api/lists/:listId/quick-add/items` (create staged + suggestions), `GET /api/lists/:listId/quick-add/memory` (stats for the settings panel). All behind the same owner/admin/item-share write boundary as any other item mutation on the board — enabling Quick Add never widens who can add to it.
- Two sweeps in `index.ts`'s `start()`: `sweepMemoryEmbeddings()` (3 min) and `sweepDirtyBubbles()` (2 min).
- **`backfillSectionMemory()` seeds the projection once** from where every existing item currently sits, so a board predicts from day one. Written in TypeScript rather than SQL specifically so it calls the REAL `titleKey()` — a hand-rolled SQL equivalent would be a second normalization implementation that has to stay byte-identical forever, and the day they drift every seeded row silently stops matching. Guarded by an `app_settings` flag; its rows use `ON CONFLICT DO NOTHING` so live memory always wins over a backfill of the same fact.
- Keyboard shortcut **`q`** (`quick-add`), deliberately distinct from **`i`** (`create-item`, which still focuses a *section's* own add field): Quick Add is the board's front door, a section's field is for when you already know where it goes.
- **Known V1 gaps:** memory is strictly per-board (no cross-board learning by section label); the tray has no bulk "file everything" action; the rendered bubble table caps at 100 rows (and says so) though all rows still inform suggestions.

### Keyboard Shortcuts

- **`frontend/src/shortcuts/registry.ts`** is the single source of truth for every global keyboard shortcut: `SHORTCUT_DEFS` lists each action's id, label, description, default key combo, and scope. Adding a new shortcut means adding one entry here — nothing else needs a hardcoded key check.
- **`frontend/src/store/useShortcutsStore.ts`** holds the signed-in user's per-shortcut overrides (custom key and/or enabled/disabled), persisted to `users.keyboard_shortcuts` (JSONB) via `PUT /api/auth/shortcuts` and hydrated on login/register/2FA-verify (`sanitizeUser` in `routes/auth.ts` includes `keyboardShortcuts`). Only overrides are stored — an action absent from the map falls back to the registry's default, so new shortcuts need no migration or backfill. A local zustand `persist` cache (localStorage) makes the bindings available instantly on reload, ahead of any network round trip.
- **`frontend/src/components/KeyboardShortcuts.tsx`** is mounted once in `AppLayout` and owns the one `document.addEventListener('keydown', …)` for the whole feature. It ignores keydowns while an input/textarea/select/contenteditable is focused, matches the combo against the merged bindings, and either performs the action directly (e.g. the sidebar-collapse store toggle) or dispatches a `window` `CustomEvent` named `shortcut:<id>` — the same cross-component signal pattern already used for `gps-upload-trigger`/`gps-files-changed`. Whichever screen/component is mounted (or not) picks it up; e.g. `ListScreen` listens for `shortcut:create-item`, `TimelineScreen`'s `MilestoneEditor` listens for `shortcut:delete-current` only while `onDelete` is available (edit mode).
- Users manage their bindings in **Account Settings → Controls** (`ShortcutsSection` in `UserSettingsModal.tsx`): each shortcut can be rebound (click the combo, press a new one — rejects browser-reserved combos and combos already used by another enabled shortcut), turned off, or reset to default individually or all at once.
- **Every non-trivial UI feature needs a shortcut.** When implementing a new screen, panel, toggle, or dialog action of any real significance (not a one-off cosmetic tweak), add a corresponding entry to `SHORTCUT_DEFS` and wire its `shortcut:<id>` listener — don't wait to be asked. Pick an unused default key, a `scope` that matches where it applies, and confirm the entry surfaces automatically in `ShortcutsSection` (it does, by construction — see above).

Vitest is the standard for new tests in both packages; add backend tests under `src/__tests__/`.

**Beyond that default suite** there is a second, DB-backed one: `*.integration.test.ts` (`npm run test:integration`) runs against a real Postgres and covers what a mock `QueryExec` cannot — optimistic-concurrency races, atomic reorder, pool saturation, the multi-replica scheduler, SSE revocation, the OAuth flow, and the "Shared with members" folder cascade (`itemShares.integration.test.ts` — a mock can prove which SQL was issued, only a real database can prove it retrieves the right rows and stops at the folder boundary). Each file skips loudly rather than failing when no database is reachable, so CI asserts connectivity FIRST: a skipped suite is still a green suite, and a service container that failed to start must not read as a pass. CI runs it against `pgvector/pgvector:pg16` — the same image `docker-compose.yml` ships — so the Knowledge Layer's pgvector paths are exercised rather than only its lexical-only fallback. Live LLM/embedding-provider calls remain out of scope and are exercised with mocked providers.

Beyond automated tests, verify manually:
- Backend: `curl` or a REST client against `http://localhost:3001`
- Frontend: run the dev server and test in browser

## Security Notes

These issues were identified and fixed (see `security_report.md`). Do not regress them:

1. **IDOR** — All DB queries must filter by `user_id = $userId` extracted from the verified JWT, never from request body/params alone. Workspace-scoped reads must additionally honor membership/visibility (see `workspaceUtil.ts`).
2. **JWT_SECRET** — Must be a strong random secret. Backend exits in production if it is the placeholder default. `token_version` allows mass-invalidating tokens.
3. **Rate limiting** — Auth, 2FA, setup, and destructive endpoints have tighter limits. Do not remove these.
4. **File path traversal** — Use `path.resolve` / `path.join` carefully when serving files (shared files, attachments, GPS files). Validate that the resolved path stays within its upload dir.
5. **Profile image uploads** — Validate MIME type and file extension server-side before saving.
6. **Password hashing** — Always use `bcryptjs` for account passwords AND share-link passwords. Never log or return hashes.
7. **Race conditions** — Storage quota checks must be done inside a transaction or with `SELECT ... FOR UPDATE` to prevent over-quota uploads under concurrent load.
8. **Public share endpoints** — `/api/share/*` are intentionally unauthenticated. They must only ever expose data when the relevant `share_enabled`/`is_public` flag is set, must enforce password + expiry, and must never leak owner-only fields (hashes, internal IDs, private sibling data).
9. **Per-item invitation cascade** — a share grant is stored on ONE row and resolved over the containment tree; the read fragment (`itemShareExists`) and the runtime write check (`isItemSharedWith`) must stay equivalent, or a user ends up able to read but not write (or worse, the reverse). Both live in `backend/src/itemShares.ts` and nowhere else — never hand-roll an `item_shares` lookup at a call site. `removeItemShare` deletes only the DIRECT grant by design: an inherited member is revoked on the folder that granted them, and the UI must not offer a Remove button that would silently delete nothing.
10. **Graph Layer visibility boundary** — `entity_index`/`entity_links` must NEVER be queried directly from a route or from any module other than `graph/entityIndex.ts`/`graph/links.ts`, and those must always scope through `graph/visibility.ts`'s `isEntityVisible`/`canWriteEntity`. A miss must 404, never 403 — an entity a caller can't see must be indistinguishable from one that doesn't exist. `entity_chunks` (Knowledge Layer) is held to the same rule — never queried without joining through `entity_index` + `visibleCondition`.
11. **Agent Runtime scope** — an agent run has no capabilities beyond the shared `aiTools.ts` registry's own `userId`-scoped queries, further narrowed by its workspace's `agent_policy` (allow/deny lists, run limits, approval thresholds). The 6 Agent Runtime meta-tools are `mcpOnly` and excluded from the tool defs an agent run itself receives, closing an unbounded self-fork path — do not remove that flag without adding a real recursion-depth guard first (see `DEPRECATIONS.md`).
12. **AI Skills are admin-only to write, and never executable** — every `create_skill`/`update_skill`/`delete_skill`/`set_skill_file`/`remove_skill_file` tool handler (and every `routes/aiSkills.ts` REST route) re-derives admin status from `users.is_admin` rather than trusting anything the caller/model claims, since a tool handler only ever receives a `userId`, never a role. `.zip` bundle uploads are parsed by a dedicated, pure `parseSkillBundle()` (`aiSkills/bundle.ts`) that validates every entry path before ever joining it with a filesystem/DB write (zip-slip) and enforces size/count caps from the archive's declared metadata before reading any entry content (zip-bomb) — do not add a code-execution path to bundled files; the app's one narrow sandbox for untrusted code is the Automation Hub's `isolated-vm`, and it stays that way on purpose.

## Key Architectural Decisions

- **Migrations in code, not files** — `runMigrations()` in `index.ts` uses `IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS` guards and idempotent data heals/seeds. Always append new migrations there.
- **No ORM** — Raw SQL keeps queries explicit and avoids N+1 pitfalls; use `JOIN` freely.
- **Zustand over Redux** — Minimal boilerplate; each store is a standalone module. Stores call the API client directly; components call store actions.
- **Soft delete** — Deleted tasks, lists, folders, and timelines go to their respective `trash*` tables (JSONB payload) with a 30-day `expires_at`. The live tables have no `deleted_at` column.
- **Task IDs are BIGINT** — Generated client-side as `Date.now()` (milliseconds). Per-user FK scoping prevents cross-user collisions; avoid relying on global uniqueness.
- **Workspaces scope everything** — Lists, folders, tasks, and timelines carry a `workspace_id`. Every user gets an auto-seeded private "Personal" workspace. Workspace `visibility` (`private｜public`) plus `workspace_members` govern who can see shared content in-app.
- **Two distinct notions of "public":**
  1. `is_public` on lists/folders/timelines = **in-app visibility to workspace members**.
  2. `share_enabled` + `share_token` = **anonymous read-only link** for anyone on the internet (no login), optionally password-protected and/or time-limited. These are independent — enabling one does not enable the other.
- **Real-time via a cursor-based delta-sync engine over SSE** — `sync_log` (`BIGSERIAL seq`) is a transactional outbox: `AFTER INSERT/UPDATE/DELETE` triggers on every synced table (see `runMigrations()`) append a row and `pg_notify` a compact descriptor. `backend/src/syncLog.ts` LISTENs, resolves the audience (workspace members + owner + public contributors), and pushes a cursor-tagged frame over `/api/events` via `broadcastToUsers` (`sse.ts`) — this is what makes a collaborator's edit appear live on every device that can see it, not just the author's. The frame is a nudge only; `GET /api/sync/bootstrap` (full state + cursor) and `GET /api/sync/delta?since=` (changes after the cursor, re-serialized fresh and scoped to the requesting user — the real access boundary) are authoritative. `frontend/src/store/useSyncStore.ts` owns the cursor and applies deltas into `useAppStore` (`applyDeltas`/`hydrateFromSnapshot`) without a full reload. Live by default; `VITE_SYNC_ENGINE=0` reverts to the legacy full/slice-reload loader (`useAppStore.loadFromApi`) as an instant rollback. No WebSocket server, no Redis — a single in-process dispatcher, deliberately isolated so a Redis backplane could replace it later without touching call sites.
- **AI via OpenRouter** — The AI endpoint is a thin proxy. Model and enabled state live in `app_settings` so admins can change them without redeployment. Chat sessions and uploaded files expire after 30 days.
- **GPS route state is versioned** — `gps_files.route_state` is `GpsRouteStateV1`; bump the version and migrate the shape if its structure changes.
- **Graph Layer is additive, not a replacement** — the 5 legacy hard-link mechanisms (sublists, task↔list links, markdown-page Todo sync, both attachment tables) keep their existing columns/tables as the source of truth; `entity_links` only mirrors them (`origin = 'system'`) alongside. A real composite FK from `entity_links` to `entity_index` (rather than a polymorphic reference with no FK at all) is what makes edges safe despite `tasks.id` being `BIGINT` while every other entity id is `VARCHAR(100)` — `entity_id` is always stored/compared as a string. Every DB read/write for this feature funnels through `graph/visibility.ts`; see "Graph Layer" above.
- **The legacy-column drop is a two-key gate, not a timer** — `runMigrations()` carries a dormant `DROP COLUMN`/`DROP TRIGGER`/`DROP FUNCTION` block for the 3 pure-reference legacy columns (`tasks.linked_list_id`, `lists.parent_task_id`, `markdown_lists.todo_list_id`), but it only fires once BOTH `app_settings.graph_migration_verified` (written only by `graph/verifyMigration.ts`'s nightly sweep, after 7 consecutive drift-free days) AND `app_settings.graph_links_v2` (a read-switch flag this codebase never sets — it exists specifically so drift-verification alone can never be sufficient) are `'true'`. The gate exists because the `trg_hardlink_*` sync triggers still reference these columns via `NEW.column_name`; dropping them without also retiring the triggers in the same statement would break every subsequent write to the underlying tables. See `DEPRECATIONS.md` for the full phase table and why R4 (the application read-switch) is explicitly out of scope for this rollout.
- **The Knowledge BASE is a dictionary, the Knowledge LAYER is a search engine** — and the difference is the whole reason both exist. `knowledge_search` ranks CONTENT by relevance and is allowed to be approximately right; `lookup_knowledge` resolves a TERM and is not. It returns a definition or an explicit "not defined" with near-misses, and never silently degrades into similarity matching, because a model about to state a fact about the user's own vocabulary is better served by a clean miss than by a 60%-right guess. The two are complementary, not redundant: entries are indexed into `entity_chunks` like everything else, so a semantic search still surfaces them.
- **The Knowledge Base reuses the substrate rather than forking one** — `entity_index` + `entity_links` for nodes and edges, the shared `BlockEditor` and `buildMarkdownBlockFromSpec` for bodies, `embedding_queue` for indexing, `aiTools.ts` for AI/MCP reach. The genuinely new code is the dictionary semantics (term/alias uniqueness, exactness-first lookup) and the net UI. A workspace has exactly one base, enforced by a `UNIQUE` constraint rather than an application check, for the same reason `entity_links` carries a real composite FK: a database invariant cannot be forgotten by a second code path.
- **Knowledge Layer degrades gracefully, never hard-fails** — pgvector, an embedding provider, and a configured token budget are all optional; absent any of them, `knowledge/search.ts` still returns lexical-only (trigram) results rather than erroring. No feature flag needs to be flipped in lockstep with infrastructure availability — the code checks reality (`isPgvectorAvailable()`, whether an embedding key is configured) rather than trusting a setting to match it.
- **Agent Runtime reuses the tool registry, it doesn't fork one** — an agent run, Sol, and the MCP server all execute through the exact same `aiTools.ts` handlers and the exact same `userId`-scoped security invariant; the only per-consumer difference is which subset of tool defs each one is handed (`getOpenRouterToolDefs()` excludes `mcpOnly` tools; `getMcpToolDefs()` includes everything). This means a new tool is automatically available to all three consumers by construction, and a security fix to a handler automatically covers all three as well.
- **AI Skills are instance-wide admin content, not per-user or per-workspace** — deliberately the odd one out among this app's mostly workspace-scoped features. A skill exists to make every user's assistant smarter/more consistent on this instance, so there is no natural per-workspace owner the way a Knowledge Base has one; write access is a flat admin check instead of a membership check, and the "enabled skill" index is a single instance-wide list every session loads once. Progressive disclosure (name+description always in context, full body fetched via `read_skill` on demand) reuses the exact split `lookup_knowledge`/the Knowledge Base glossary already established — a second instance of the same idea, not a new one.
- **Admin API is scoped** — `admin_api_keys` are instance-wide credentials (created by admins, hashed, revocable) that carry a `scopes` JSONB array. `routes/adminReadApi.ts` (mounted at `/api/admin-read`) gates each route behind a scope from `ADMIN_API_SCOPES` in `adminApiKey.ts` (`read`, `users`, `workspaces`, `folders`, `lists`, `timelines`, `meetings`); the creation wizard (`modals/AdminApiKeyWizard.tsx`) toggles them. Beyond `read` (the export), it supports full create/update/delete for those resources on behalf of any user — the target owner comes from an explicit, validated `ownerId` (defaulting to the key creator), never trusted blindly. Add new scopes to `ADMIN_API_SCOPES` and `ADMIN_API_FEATURES` together.
- **Admin Nuke is a total, self-restarting instance reset** — `DELETE /api/admin/nuke` (`routes/admin.ts`, admin-only + password re-check) discovers every table in the `public` schema via `pg_tables` (never a hardcoded list — a fixed list silently stops covering new tables as the schema grows) and `TRUNCATE`s all of them in one statement, deletes every file under `UPLOAD_DIR` (shared files, task/milestone attachments, GPS/FIT tracks all live flatly there), regenerates the setup token, then broadcasts a dedicated `event: nuke` SSE frame to **every** connected client of **every** user (`broadcastToUsers`'s sibling `broadcastNukeToAll` in `sse.ts` — a `TRUNCATE` doesn't fire row-level triggers, so this bypasses the normal sync_log pipeline entirely) telling each tab to clear its storage and land on `/setup` immediately, rather than waiting for its next API call to 401. It then calls `process.exit(0)` after a short delay so Docker Compose's `restart: unless-stopped` policy relaunches a fully clean process — the only way to guarantee no in-memory state (the SSE registry, rate-limiter counters, the sync dispatcher's LISTEN connection) survives. Set `NUKE_SKIP_RESTART=true` to opt out when running without a process supervisor that will bring the process back up.
